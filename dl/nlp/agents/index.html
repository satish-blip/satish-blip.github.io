AI agents and how to evaluate them

A chat model answers once. An agent is the same model put in a loop: it decides which tool to call, your code runs the tool, the result goes back in, and the model decides again, until the job is done. This page builds that loop from its parts: tool calls checked against a schema, the loop itself and the maths of why long tasks fail, how an agent remembers, and then the harder question of measuring any of it, with retrieval metrics computed claim by claim and an LLM judge whose biases you can switch on.

What is an agent, in plain words?

The problem

A language model only produces text. It cannot look up today's weather, run code, read your files or book a meeting, and whatever it knows stops at its training date. Many useful jobs also take several steps whose order is not known in advance: search, read, notice something is missing, search again. How do we let a text predictor act in the world, and how do we know whether it is doing a good job?

The idea

Describe each tool to the model with a name, a sentence and a JSON schema for its arguments. When the model wants a tool it writes a structured tool call instead of an answer; your program runs it and sends back the result. Repeat in a loop, and you have an agent. Measuring it needs new metrics too, because answers are free text: faithfulness and context recall for retrieval, and often another model acting as judge.

How it works

  1. Give the model a task and the list of tools it may use.
  2. The model replies with text, or with one or more tool calls.
  3. Your code checks the arguments, runs the tools and returns the results.
  4. Loop until the model answers without calling a tool, or a step limit is hit.
  5. Evaluate whole runs, not just single replies: did it finish, was it right, was it grounded?

An everyday picture

A new assistant on their first day with a phone, a calculator and a filing cabinet. You give them a job (“find out what we spent on travel last quarter”). They decide whom to ring, read what they get back, do the sums and come back with an answer. They are only as good as the instructions on each tool, they forget things unless they write them down, and you check their work by asking whether every number in the report came from a document they actually read.

Good at
  • Fresh or private information through search and databases
  • Exact work handed to real tools (code, maths, APIs)
  • Open-ended tasks where the steps are not known in advance
Watch out for
  • Small per-step error rates multiply over long tasks
  • Hallucinated tools or arguments; actions that cannot be undone
  • Judging free text is hard, and LLM judges have biases of their own

1Tool calling: a contract written in JSON

The tool below is described to the model by its schema. Pick a call the model might write, or edit it yourself, and watch your code's validator decide what goes back.

Tool definition sent with the request
Tool call written by the model (editable)
What your code sends back

Modern chat APIs let you pass a list of tools with every request. Each tool has a name, a description written for the model, and an input schema in JSON Schema: which arguments exist, their types, which are required, and allowed values. The model never runs anything. It replies with a tool call, a block such as {"name": "get_weather", "input": {"city": "Paris"}} with an id, and stops. Your program runs the function and replies with a tool result carrying the same id. The model then continues, now knowing the answer.

Why a schema? Because the call is text produced by sampling, so it can be wrong in every way text can: a missing field, a number written as a word, a value outside the list, or a tool that does not exist. Constrained decoding (some APIs offer a “strict” mode that only lets the model produce tokens that keep the JSON valid against the schema) removes the format errors, but not the wrong choices: calling the right tool with the wrong city is still valid JSON.

Let a call fail loudly and usefully. When validation fails, send a tool result marked as an error with a message the model can act on (“unit must be one of celsius, fahrenheit”). Models are good at repairing a call from a clear error, so one retry usually fixes it. Silent failures, where the tool returns an empty string or a default, are the dangerous ones, because the model carries on as if they succeeded.

$$\big(\text{messages},\ \{\text{name}_j,\text{desc}_j,\text{schema}_j\}\big)\ \longrightarrow\ \text{text}\ \ \text{or}\ \ \text{call}(\text{name},\text{args},\text{id})$$
Going deeper: how a model learns to call tools at all

Tool use is taught in post-training. Toolformer (Schick et al., 2023) showed a model can label its own training text with API calls, keeping only those that lowered the loss on the following tokens. Today's assistants are fine-tuned on many conversations that contain tool definitions, calls and results, using a chat template with special tokens for each part, and then trained further with preferences or reinforcement learning on tasks that need tools.

Because the definitions sit in the prompt, every tool costs tokens on every call, and the model's choice depends on how clearly the descriptions separate tools. Good descriptions say when to use the tool and when not to, what each argument means, and what the result looks like. Ten well-described tools often beat fifty vague ones.

Adapted from: Anthropic, Tool use with Claude documentation; Schick et al., Toolformer (2023); Understanding JSON Schema.

2The agent loop, and why long tasks fail

A task needs n steps; each succeeds with probability p. A failed step may be noticed (an error comes back) and retried. Watch task success fall with length, then see how much error detection buys back.

Each row is one simulated run, each square a step: green succeeded first time, amber succeeded after a retry, red failed (the run stops), grey never reached.

The loop is short enough to write in full. Everything interesting lives in what the model decides at line 4 and what your code does at line 6.

Algorithm: a tool-using agent
  1. input task \(q\); tools \(\mathcal T\) with schemas; step limit \(K\)
  2. \(M\leftarrow[\text{system prompt},\,q]\) the message history
  3. for \(k=1,\dots,K\)
  4. \(y\leftarrow\text{LLM}(M,\mathcal T)\)
  5. if \(y\) has no tool call: return \(y\) final answer
  6. for each call \((t,a,\text{id})\in y\): validate \(a\) against \(t\)'s schema, run \(t(a)\) or build an error
  7. append \(y\) and every result (matched by id) to \(M\)
  8. return “step limit reached” always have a stop

Now the arithmetic. If each step succeeds independently with probability \(p\), a task of \(n\) steps succeeds with \(p^n\). At \(p=0.95\), ten steps succeed 60% of the time and fifty steps 8%. This is compounding error, and it is why agents that look good in a demo struggle on long jobs.

Retries help only when a failure is noticed. Let a fraction \(d\) of failures come back as visible errors (a schema check, an exception, a failing test) and allow up to \(r\) retries. A step then succeeds if attempt \(k+1\) succeeds after \(k\) detected failures:

$$P_{\text{step}}=p\sum_{k=0}^{r}\big((1-p)\,d\big)^k,$$$$P_{\text{task}}=P_{\text{step}}^{\,n},\qquad \mathbb E[\text{calls per step}]=\sum_{k=0}^{r}\big((1-p)\,d\big)^k .$$

Set \(d=0\) in the lab and retries do nothing; raise \(d\) and the curve lifts sharply for a small rise in calls. That is the case for strict schemas, tests, assertions and tools that return clear errors: they turn silent failures into detected ones.

Going deeper: workflows versus agents, and the independence assumption

Independence is an approximation. Real errors are correlated (one misunderstanding spoils many steps), and a good agent can also recover from an earlier mistake it notices later, which this model ignores. The lesson still holds: fewer, more reliable steps beat many fragile ones.

That is why many production systems are workflows rather than free agents: the code fixes the sequence of steps (classify, retrieve, draft, check) and the model fills each one in. Agents earn their cost when the path really cannot be known in advance. Useful patterns in between are routing (a cheap call picks which workflow runs), orchestrator–workers (one call splits a task, others do the parts), and evaluator–optimiser (one call drafts, another critiques, repeat).

Adapted from: Yao et al., ReAct: Synergizing Reasoning and Acting in Language Models (2022); Anthropic, Building effective agents (2024). The retry formula is this page's own simple model.

3Memory: what the agent can still see

A long conversation, one fact mentioned some turns ago, and a question about it now. Compare four ways of deciding what goes into the next prompt: how likely is the fact to be there, and how many tokens does each call cost?

The model itself remembers nothing between calls. Everything it knows about the conversation is in the prompt, and the prompt must fit the context window. Long chats and long agent runs outgrow it, and even when they fit, every call pays for every token again. So agent memory is really a policy for building the next prompt. Four common ones (assume about 300 tokens per turn and a 128k-token window):

  • Full history. Send everything. Perfect recall until the window fills, after which the call simply fails. Cost grows linearly with the length of the chat, so total cost grows with its square.
  • Sliding window. Keep the last \(k\) turns. Cheap and predictable, but anything older is gone completely.
  • Summary. Keep the last \(k\) turns and a running summary of the rest, rewritten every \(k\) turns. A fact that has been through \(m\) rewrites survives with probability \(s^m\), so old details fade.
  • Retrieval. Store every turn (or extracted facts) in a vector index, embed the current question and fetch the most similar items, as in RAG. Recall no longer depends on age, only on whether the search finds it.
$$\text{recall}_{\text{summary}}(a)=\begin{cases}1,&a\le k\\ s^{\lceil (a-k)/k\rceil},&a>k\end{cases}$$$$\text{recall}_{\text{retrieval}}(a)=1-(1-\rho)^{m}$$

Here \(a\) is the fact's age in turns and, for retrieval, \(m\) is the number of memories fetched and \(\rho\) a per-item chance of hitting the right one (0.35 in the lab: a toy number). Real systems mix them: a short verbatim window, a summary for the gist, retrieval for details, and explicit notes the agent writes to a file or scratchpad for facts it knows it will need.

Going deeper: lost in the middle, and memory the agent writes itself

Fitting in the window is not the same as being used. Liu et al. (2023) found models answer best when the relevant passage sits at the start or end of a long prompt and worst when it is in the middle. Putting retrieved facts close to the question, and keeping prompts lean, often helps more than a bigger window.

Agents that run for hours work better with structured memory: a to-do list, a progress file, notes on decisions. MemGPT (Packer et al., 2023) treats the window like RAM and an external store like disk, with tools to page facts in and out. Some APIs also clear old tool results automatically once they have been used.

Adapted from: Liu et al., Lost in the Middle (2023); Packer et al., MemGPT (2023). Recall curves are a simplified model for teaching, not measurements.

4RAG metrics, claim by claim

Question: When was the Eiffel Tower completed, and how tall is it? Reference answer: completed in 1889; about 330 m tall. Choose which chunks the retriever returned, in which order, and which claims the answer makes.

Retrieved chunks (rank order)
Claims in the generated answer

A RAG answer can go wrong in two places: the retriever fetched the wrong passages, or the generator ignored or embellished them. Exact-match scores (used in the RAG papers) need a single right string. For free-text answers the RAGAS family of metrics breaks the text into claims (short factual statements) and asks, one claim at a time, whether it is supported. An LLM usually does the splitting and checking; here the verdicts are fixed so you can see the arithmetic.

Faithfulness checks the generator: what share of the answer's claims can be inferred from the retrieved context?

$$\text{faithfulness}=\frac{\#\{\text{answer claims supported by the context}\}}{\#\{\text{answer claims}\}}$$

Context recall checks the retriever against the reference answer: what share of the reference's claims appear in what was retrieved? Context precision checks the ranking: are the useful chunks near the top? With \(v_k=1\) if the chunk at rank \(k\) is relevant,

$$\text{context precision@}K=\frac{\sum_{k=1}^{K}\text{precision@}k\cdot v_k}{\#\{\text{relevant in the top }K\}}$$$$\text{precision@}k=\frac{1}{k}\sum_{i\le k}v_i$$

Two lessons from the lab. First, faithful is not the same as true: “it was the tallest structure in the world until 1930” is correct, but it is not in the context, so it lowers faithfulness; in a RAG system, an unsupported true claim is a claim you cannot check. Second, the metrics separate the blame: low recall means fix retrieval, low faithfulness with good recall means fix the prompt or the model.

Going deeper: answer relevancy, and checking the checker

Answer relevancy asks whether the answer addresses the question at all: an LLM writes several questions the answer would fit, and the score is their average embedding similarity to the real question. A faithful answer to a different question scores low.

Every one of these metrics is computed by a model, so it has its own error rate. Before trusting a dashboard, label 50–100 examples by hand and measure how often the metric agrees with you, exactly as in the next section. Keep a fixed test set, compare systems on the same questions, and report the spread across questions, not just the mean.

Adapted from: Es et al., RAGAS: Automated Evaluation of Retrieval Augmented Generation (2023) and the ragas documentation (metric definitions).

5LLM-as-a-judge, and its biases

300 simulated questions, each with two answers of hidden quality and a human verdict. A judge model compares them, but it also leans towards whichever answer it reads first and towards the longer one. Turn the biases up, then try the swap test.

Grading free text by hand does not scale, so a strong model is often asked to do it: “Here is a question and two answers. Which is better? Explain, then say A, B or tie.” This LLM-as-a-judge setup agrees with human raters about as often as humans agree with each other on many chat benchmarks (around 80% in the MT-Bench study), but it has systematic biases:

  • Position bias: preferring the answer shown first (or second).
  • Verbosity bias: preferring longer answers even when they add nothing.
  • Self-preference: preferring answers written in its own style or by its own model family.

The cheapest fix is the swap test: judge every pair twice with the order reversed, and accept a winner only if both verdicts agree; otherwise call it a tie. Position bias then cancels by construction: in the lab the judge stops favouring A (among the pairs it decides, A and B win about equally often, as with the humans), and agreement on those pairs rises. The price is more ties (the close calls the judge could not separate) and twice the cost, and the share of pairs that flip is itself a useful warning light.

Algorithm: pairwise judging with the swap test
  1. input question \(q\), answers \(A, B\), judge prompt
  2. \(v_1\leftarrow\text{judge}(q, A, B)\) A shown first
  3. \(v_2\leftarrow\text{judge}(q, B, A)\) B shown first; map back to A/B
  4. if \(v_1=v_2\): return \(v_1\)
  5. else: return tie the verdict depended on order
  6. over all questions: win rate, consistency, and agreement with human labels (κ)

How do we know the judge is any good? Compare it with human labels on a sample. Raw agreement flatters a judge that always says “A” when A usually wins, so we use Cohen's kappa, which subtracts the agreement expected by chance:

$$\kappa=\frac{p_o-p_e}{1-p_e},\qquad p_e=\sum_{c}p_{\text{judge}}(c)\,p_{\text{human}}(c),$$

where \(p_o\) is the observed agreement and \(p_e\) the agreement two raters would reach by chance with the same label frequencies. \(\kappa=1\) is perfect, 0 is chance. In the lab, the simulation draws a hidden quality gap \(\Delta\) for each pair and a length gap \(\ell\); humans see \(\Delta\) plus noise, and the judge prefers the first-shown answer with log-odds \(\Delta+b_{\text{pos}}+b_{\text{len}}\ell+\varepsilon\).

Going deeper: rubrics, reference answers and single-answer grading

Pairwise comparison is the most reliable format, but you can also grade one answer on a 1–10 scale against a rubric, or against a reference answer for questions with a right answer. Rubrics with concrete criteria (“mentions the dosage; cites a source; no unsupported claims”) are more stable than “rate the quality”. Asking the judge to reason before giving its verdict helps; so does a stronger judge than the model being judged.

For agents, judge the trajectory too: did it use the right tools, did it stop, did it take any action it should not have? Many agent benchmarks avoid judges altogether by checking the final state of an environment (the test suite passes, the booking exists), which is the most trustworthy signal when you can get it.

Adapted from: Zheng et al., Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena (2023); Cohen (1960), A coefficient of agreement for nominal scales.

6The same thing in Python

A complete tool-using agent loop with the Anthropic Python SDK, then a pairwise judge with the swap test. Needs an API key in ANTHROPIC_API_KEY.

# pip install anthropic
import json
import anthropic

client = anthropic.Anthropic()
MODEL = "claude-opus-5-5"

# ---- 1. Tools: a schema the model sees, and the Python that runs it ----
tools = [{
    "name": "get_weather",
    "description": "Current weather for a city. Use when the user asks about weather now.",
    "input_schema": {
        "type": "object",
        "properties": {
            "city": {"type": "string", "description": "City name, e.g. Paris"},
            "unit": {"type": "string", "enum": ["celsius", "fahrenheit"]},
        },
        "required": ["city"],
    },
}]

def get_weather(city, unit="celsius"):
    fake = {"paris": 14, "london": 11, "delhi": 31}           # stand-in for a real API
    if city.lower() not in fake:
        raise ValueError(f"Unknown city '{city}'. Try a major city name.")
    t = fake[city.lower()]
    return json.dumps({"city": city, "temp": t if unit == "celsius" else t * 9 / 5 + 32, "unit": unit})

RUN = {"get_weather": get_weather}

# ---- 2. The agent loop ----
def agent(task, max_steps=8):
    messages = [{"role": "user", "content": task}]
    for step in range(max_steps):
        response = client.messages.create(model=MODEL, max_tokens=4096,
                                          tools=tools, messages=messages)
        if response.stop_reason != "tool_use":                # end_turn, refusal, max_tokens...
            return "".join(b.text for b in response.content if b.type == "text")
        messages.append({"role": "assistant", "content": response.content})
        results = []
        for block in response.content:
            if block.type != "tool_use":
                continue
            try:
                out, err = RUN[block.name](**block.input), False
            except Exception as e:                            # unknown tool, bad args, API error
                out, err = f"Error: {e}", True
            results.append({"type": "tool_result", "tool_use_id": block.id,
                            "content": out, "is_error": err})
        messages.append({"role": "user", "content": results})  # all results in one message
    return "Stopped: step limit reached."

print(agent("Is it warmer in Paris or London right now, in fahrenheit?"))

# ---- 3. LLM-as-a-judge with the swap test ----
JUDGE = ("You are comparing two answers to the same question. Judge accuracy and "
         "helpfulness only; ignore length and order. Think briefly, then end with a "
         "final line containing exactly one of: WINNER: 1, WINNER: 2, WINNER: TIE.")

def judge_once(question, first, second):
    msg = client.messages.create(model=MODEL, max_tokens=1024, system=JUDGE, messages=[{
        "role": "user",
        "content": f"Question:\n{question}\n\nAnswer 1:\n{first}\n\nAnswer 2:\n{second}"}])
    text = "".join(b.text for b in msg.content if b.type == "text")
    last = text.strip().splitlines()[-1].upper()
    return "1" if "WINNER: 1" in last else "2" if "WINNER: 2" in last else "tie"

def judge_pair(question, a, b):
    v1 = {"1": "A", "2": "B"}.get(judge_once(question, a, b), "tie")   # A shown first
    v2 = {"1": "B", "2": "A"}.get(judge_once(question, b, a), "tie")   # B shown first
    return v1 if v1 == v2 else "tie"                                    # order-dependent: tie

# ---- 4. Agreement with your own labels: Cohen's kappa ----
from sklearn.metrics import cohen_kappa_score
human = ["A", "B", "A", "A", "B", "tie"]
judged = ["A", "B", "tie", "A", "B", "tie"]                  # from judge_pair over the same items
print("kappa =", round(cohen_kappa_score(human, judged), 3))

For RAG metrics, the ragas library implements faithfulness, context recall, context precision and answer relevancy over a dataset of questions, retrieved contexts, answers and references; its API changes between versions, so follow the docs for the version you install.
