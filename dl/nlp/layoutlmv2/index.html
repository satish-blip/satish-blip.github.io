LayoutLMv2: reading documents with text, layout and image

A receipt is not a sentence. "13.55" means nothing until you notice that it sits on the same line as "TOTAL", in bold, at the bottom of the page. The models in parts 1 to 4 paired photos with captions. LayoutLMv2 (Xu et al., 2021) pairs the text of a scanned page with where each word is and what the page looks like, and it became a standard model for document understanding. This page builds its input, probes its attention, walks through how it is pre-trained, and uses it to pull fields out of documents.

What is LayoutLMv2, in plain words?

The problem

Businesses process millions of receipts, invoices, forms and contracts. The task is called document AI: given a scanned page, find the total, the date, the customer's name, the line items. An OCR engine can already turn the scan into words, each with a bounding box. But if we feed those words to BERT as one long sentence, we throw away the layout, and the layout carries most of the meaning: a value is usually to the right of, or just below, its label.

The idea

LayoutLM (2020) added a 2-D position embedding to every word, built from its box. LayoutLMv2 (2021) goes further in three ways. It puts the page image into the same transformer as visual tokens; it adds spatial-aware self-attention, so attention scores depend on the relative position of two words on the page; and it is pre-trained with jobs that tie text and image together: masked visual-language modelling, text–image alignment and text–image matching.

How it works

  1. Run OCR: words plus their boxes, scaled to a 0–1000 grid.
  2. Turn the page image into 49 visual tokens with a CNN.
  3. Give every token a 1-D position, a 2-D layout embedding and a segment.
  4. Run a transformer whose attention knows distances on the page.
  5. Fine-tune: for example, tag each word as part of a field with BIO tags.

An everyday picture

Hand someone a restaurant bill in a language they cannot read, and ask for the total. They still find it at once: bottom of the page, the biggest number, in bold, at the end of the line that starts with a short word. They used layout and appearance, not meaning. LayoutLMv2 is built to use all three: meaning, layout and appearance.

Good at
  • Forms, receipts, invoices, tables
  • Robust to odd OCR reading order
  • One model for extraction, classification and document question answering
Watch out for
  • Needs an OCR engine first, and inherits its mistakes
  • At most 512 text tokens per page
  • The CNN backbone (detectron2) is heavy to install

1From a page to tokens

Each word the OCR found has a box. Tap a word to see the numbers LayoutLMv2 actually receives for it. Switch on the 7×7 grid to see the visual tokens, and tap a cell.

Start with what the OCR engine gives us: words \(w_1,\dots,w_n\), and for each one a box with corners \((x_0,y_0)\) (top left) and \((x_1,y_1)\) (bottom right), measured in pixels. Pages come in every size, so the first step is to make the numbers comparable. Each coordinate is divided by the page width or height and multiplied by 1000:

$$\tilde x=\Big\lfloor 1000\,\frac{x}{W_{\text{page}}}\Big\rfloor,\qquad \tilde y=\Big\lfloor 1000\,\frac{y}{H_{\text{page}}}\Big\rfloor .$$

Now every page lives on the same 0–1000 grid, whatever its resolution. From the box we also take the width \(w=\tilde x_1-\tilde x_0\) and height \(h=\tilde y_1-\tilde y_0\).

Text tokens. As in BERT, each word piece gets a token embedding, a 1-D position (its place in the OCR reading order) and a segment embedding, all vectors of the model's width \(d\):

$$t_i=\operatorname{TokEmb}(w_i)+\operatorname{PosEmb1D}(i)+\operatorname{SegEmb}([A]).$$

Visual tokens. The page image is resized to \(224\times224\) and passed through a CNN (a ResNeXt with a feature pyramid). Its output feature map is average-pooled to a \(7\times7\) grid, giving 49 vectors \(f_1,\dots,f_{49}\), one per cell. A linear layer maps each to width \(d\):

$$v_j=\operatorname{Proj}(f_j)+\operatorname{PosEmb1D}(j)+\operatorname{SegEmb}([C]).$$

The segment \([C]\) tells the model "this is a picture token". Unlike the frozen detector in VisualBERT, this CNN is trained together with the rest of the model.

Layout. Every token, text or visual, also gets a 2-D layout embedding from its box (a visual token uses the box of its grid cell). Two lookup tables turn coordinates into vectors, one for the horizontal numbers and one for the vertical ones, and the results are concatenated:

$$\ell_i=\operatorname{Concat}\big(\operatorname{PosEmb2D}_x(x_0,x_1,w),\ \operatorname{PosEmb2D}_y(y_0,y_1,h)\big).$$

The layout embedding is added to both kinds of token, and the sequence is the 49 visual tokens followed by the text: \([v_1,\dots,v_{49},t_{\text{[CLS]}},t_1,\dots,t_n,t_{\text{[SEP]}}]+\ell\). Special tokens such as [CLS] get the empty box \((0,0,0,0)\).

Algorithm: building LayoutLMv2's input from a page
  1. input page image \(I\) of size \(W\times H\); OCR words \(w_1..w_n\) with pixel boxes
  2. for each box: \((x_0,y_0,x_1,y_1)\leftarrow\lfloor 1000\cdot(x_0/W,\,y_0/H,\,x_1/W,\,y_1/H)\rfloor\); \(w\leftarrow x_1-x_0\), \(h\leftarrow y_1-y_0\)
  3. text tokens: \(t_i\leftarrow\operatorname{TokEmb}(w_i)+\operatorname{PosEmb1D}(i)+\operatorname{SegEmb}([A])\)
  4. \(F\leftarrow\operatorname{CNN}(\operatorname{resize}(I,224))\); average-pool to \(7\times7\) 49 cells
  5. visual tokens: \(v_j\leftarrow\operatorname{Proj}(F_j)+\operatorname{PosEmb1D}(j)+\operatorname{SegEmb}([C])\)
  6. for every token: \(\ell\leftarrow\operatorname{Concat}(\operatorname{PosEmb2D}_x(x_0,x_1,w),\operatorname{PosEmb2D}_y(y_0,y_1,h))\) a visual token uses its cell's box
  7. \(X\leftarrow[v_1..v_{49},t_{\text{[CLS]}},t_1..t_n,t_{\text{[SEP]}}]+\ell\)
  8. return \(X\) the transformer's input
Going deeper: why a lookup table for coordinates, and why 1000

A coordinate is an integer from 0 to 1000, so it can index a learned table of 1001 vectors, exactly as a word id indexes the word-embedding table. The model then learns what "near the top" or "right edge" means instead of being told. Using a 0–1000 grid keeps the table small while still resolving positions to a tenth of a percent of the page, which is finer than a line of text.

In the original LayoutLM the four corner coordinates each had their own table and the four vectors were summed. LayoutLMv2 splits the width \(d\) into an \(x\) part and a \(y\) part, looks up \(x_0,x_1,w\) in the \(x\) tables and \(y_0,y_1,h\) in the \(y\) tables, and concatenates. Either way, two words on the same line share their \(y\) vectors, and two numbers in the same right-aligned column share their \(x_1\) vector: precisely the regularities that make a table readable.

2Spatial-aware self-attention

Tap a word to make it the query. Each box is shaded by how much attention the query gives it. Compare plain 1-D attention, LayoutLM's absolute 2-D positions, and LayoutLMv2's relative spatial bias.

Ordinary self-attention scores a pair of tokens by their content only. For a query token \(i\) and a key token \(j\), with vectors \(x_i,x_j\):

$$\alpha_{ij}=\frac{(x_iW^Q)(x_jW^K)^{\top}}{\sqrt{d_{\text{head}}}}.$$

Position enters only through the embeddings that were added at the input. On a document that is a weak signal: whether "13.55" belongs to "TOTAL" depends on their relative position (same line, to the right), not on where each one is in absolute terms.

LayoutLMv2 therefore adds three learned bias terms to every score, one for the distance in reading order and one for each axis on the page:

$$\alpha'_{ij}=\alpha_{ij}+b^{(1D)}_{\,j-i}+b^{(2D_x)}_{\,x_j-x_i}+b^{(2D_y)}_{\,y_j-y_i}.$$

Each \(b\) is a small table indexed by a (bucketed) distance, with separate values per attention head, shared across layers. Then attention proceeds as usual:

  1. \(a_{ij}=\dfrac{e^{\alpha'_{ij}}}{\sum_k e^{\alpha'_{ik}}}\): softmax over all tokens \(j\), so each row sums to 1.
  2. \(h_i=\sum_j a_{ij}\,(x_jW^V)\): the output is a weighted average of the value vectors.

Look at what the bias does in the demo. With 1-D only, "TOTAL" spreads its attention along the reading order. With the spatial bias, it concentrates on the words on its own line, and in particular on the amount to its right. A head can learn "look along my row" (large \(b^{(2D_y)}\) near 0), "look down my column" (large \(b^{(2D_x)}\) near 0), or both.

Algorithm: spatial-aware self-attention (one head)
  1. input token vectors \(x_1..x_N\) with reading positions and box corners; weights \(W^Q,W^K,W^V\); bias tables \(b^{(1D)},b^{(2D_x)},b^{(2D_y)}\)
  2. \(q_i\leftarrow x_iW^Q,\ k_j\leftarrow x_jW^K,\ v_j\leftarrow x_jW^V\)
  3. \(\alpha_{ij}\leftarrow q_i\cdot k_j/\sqrt{d_{\text{head}}}\) what the words say
  4. \(\alpha'_{ij}\leftarrow\alpha_{ij}+b^{(1D)}_{j-i}+b^{(2D_x)}_{x_j-x_i}+b^{(2D_y)}_{y_j-y_i}\) where they are
  5. \(a_{i\cdot}\leftarrow\operatorname{softmax}_j(\alpha'_{ij})\)
  6. \(h_i\leftarrow\sum_j a_{ij}v_j\)
  7. return \(h_1..h_N\)
Going deeper: why relative biases beat absolute positions

With absolute 2-D embeddings (LayoutLM v1) the score \((x_i+\ell_i)W^Q\big((x_j+\ell_j)W^K\big)^\top\) contains a cross term \(\ell_iW^QW^{K\top}\ell_j^\top\). It can, in principle, learn "same row", but it must learn it separately for every pair of absolute rows. A relative bias \(b_{y_j-y_i}\) states the rule once for all rows: same-row pairs get the same boost wherever they are on the page. That is translation invariance, the same reason convolutions share weights across positions.

Distances are bucketed (fine buckets near zero, coarse ones far away), as in T5's relative position bias, so the table stays small. The biases are computed once per forward pass and added to every layer's scores.

3Pre-training: three jobs

Pick a job and press New sample. The page image is what the CNN sees; the chips below are the text tokens in reading order, with each token's training target underneath.

LayoutLMv2 was pre-trained on about 11 million scanned pages (the IIT-CDIP collection) with no labels at all: just the images and their OCR output. Three jobs turn that raw material into a learning signal.

1. Masked visual-language modelling (MVLM). Hide about 15% of the words and predict them, as in BERT's masked language modelling, but the model keeps each hidden word's box. To guess "13.55" it may use "TOTAL" to the left and the column of prices above. One catch: the word is still visible in the page image, so its pixels are blacked out too, otherwise the CNN would simply read the answer.

$$\mathcal L_{\text{MVLM}}=-\sum_{i\in\text{masked}}\log p\big(w_i\mid h_i\big).$$

2. Text–image alignment (TIA). Pick some text lines at random and cover them in the image (the text tokens stay). For every token that is not masked, predict whether its line is covered. To answer, the model has to find the token's region in the picture, which teaches it which pixels belong to which word.

$$\mathcal L_{\text{TIA}}=-\sum_{i\notin\text{masked}}\log p\big(c_i\mid h_i\big),\qquad c_i\in\{\text{Covered},\text{Not covered}\}.$$

3. Text–image matching (TIM). For some samples the image is swapped for another page's, or left out; the output above [CLS] predicts whether text and image belong together. This is the page-level version of VisualBERT's caption matching.

$$\mathcal L=\mathcal L_{\text{MVLM}}+\mathcal L_{\text{TIA}}+\mathcal L_{\text{TIM}}.$$
Algorithm: LayoutLMv2 pre-training step
  1. input a page: image \(I\), OCR words \(w_1..w_n\) with boxes
  2. with small probability replace \(I\) by another page's image, or drop it TIM target: not matched
  3. mask 15% of the words; black out their boxes in \(I\) so the pixels cannot leak the answer
  4. cover a few random text lines in \(I\) TIA targets
  5. \(H\leftarrow\operatorname{LayoutLMv2}(\text{text},\text{layout},I)\)
  6. \(\mathcal L_{\text{MVLM}}\leftarrow\) cross-entropy of each masked word from \(h_i\)
  7. \(\mathcal L_{\text{TIA}}\leftarrow\) covered or not, for each unmasked word, from \(h_i\)
  8. \(\mathcal L_{\text{TIM}}\leftarrow\) matched or not, from \(h_{\text{[CLS]}}\)
  9. update all weights, the CNN included, to reduce \(\mathcal L_{\text{MVLM}}+\mathcal L_{\text{TIA}}+\mathcal L_{\text{TIM}}\)
Going deeper: what each job forces the model to learn

MVLM alone could be solved from the text and layout and would leave the image unused. TIA is the job that makes the image necessary: no amount of text tells you which lines were covered in the picture. It aligns each word with its pixels at a fine grain. TIM works at the coarse grain: does this text belong to this page at all? When the image is swapped or dropped, every TIA target is set to Covered, so the two jobs stay consistent.

The paper's ablations found each job helps on the downstream tasks, and that the spatial-aware attention adds a further gain on top. Pre-training the CNN jointly, rather than freezing an ImageNet model, also mattered: document images look nothing like natural photos.

4Fine-tuning: pulling fields out of a document

Coloured boxes are the predicted fields; a red outline marks a mistake. The chips show the tokens in the order the OCR returned them. Switch the OCR order to "column by column" and watch which model breaks.

The most common use is key information extraction: find the fields a business needs, such as company, date, items, prices and total. It is framed as BIO tagging, one label per token. B-TOTAL means "the first word of a total", I-TOTAL "a later word of the same total", and O "not part of any field". With \(K\) field types there are \(2K+1\) labels.

A single linear layer on top of the pre-trained model does the tagging:

$$p(y_i=c\mid\text{page})=\operatorname{softmax}\big(W h_i+b\big)_c,\qquad \mathcal L=-\sum_i\log p(y_i\mid\text{page}).$$

Fine-tuning trains \(W,b\) and adjusts all the pre-trained weights, using a few hundred labelled pages (FUNSD has 199 forms; CORD has 1,000 receipts).

Why does layout matter so much? Try the demo. The "text only" model here reads tokens in OCR order and decides from the neighbouring words, as a sequence model does. When the OCR returns the page line by line, the price follows its item and the total follows "TOTAL", and it does well. Real OCR engines often read a receipt or a form column by column, and then every price lands far from its item. The "text + layout" model decides from geometry, "what is on my row, to my left?", so the reading order no longer matters. These two models are hand-written rules standing in for what the trained networks learn, so you can see why each one succeeds or fails.

Algorithm: key information extraction with BIO tags
  1. input a page; a LayoutLMv2 fine-tuned with a token classifier \(W,b\)
  2. \(H\leftarrow\operatorname{LayoutLMv2}(\text{page})\)
  3. for each text token \(i\): \(y_i\leftarrow\arg\max_c\operatorname{softmax}(Wh_i+b)_c\)
  4. for \(i=1..n\) do
  5. if \(y_i=\)B-\(T\): close any open field; open a new field of type \(T\) with \(w_i\)
  6. else if \(y_i=\)I-\(T\) and the open field has type \(T\): append \(w_i\)
  7. else: close any open field
  8. return the list of (type, text) fields
Going deeper: other tasks, and how results are measured

Entity-level F1. A predicted field counts as correct only if its type and every one of its words match the truth exactly. Precision is the share of predicted fields that are correct, recall the share of true fields found, and F1 their harmonic mean (see evaluation metrics).

Other heads on the same model. Document classification (is this a letter, an invoice, a résumé?) puts a classifier on \(h_{\text{[CLS]}}\), as on RVL-CDIP's 16 classes. Document visual question answering (DocVQA) puts the question in the text segment and predicts the start and end token of the answer span, like extractive QA in BERT. Relation extraction links a key token to its value token with a small pairwise classifier.

Two directions after v2. LayoutLMv3 kept the OCR words but replaced the CNN with image patches, as in the Vision Transformer, and added a masked-image job so text and image are learned symmetrically. Donut and Pix2Struct dropped OCR altogether: an image encoder reads the pixels and a decoder writes out the answer as text, which avoids OCR errors at the cost of more training.

Today's multimodal LLMs read documents the same way they read photos, with visual tokens fed to a language model. LayoutLMv2's ideas still carry over: give the model where things are, not just what they say, and train it on jobs that force text and pixels to agree.

Going deeper: model sizes and training data

LayoutLMv2-base has 12 transformer layers of width 768 (about 200 million parameters including the visual backbone); the large model has 24 layers of width 1024 (about 426 million). Both were initialised from UniLMv2 text weights and pre-trained on IIT-CDIP. The paper reports state-of-the-art results at the time on FUNSD (forms), CORD and SROIE (receipts), Kleister-NDA (long contracts), RVL-CDIP (document classification) and DocVQA (question answering).

The input is capped at 512 text tokens plus 49 visual tokens. Longer documents are split into windows, and very dense pages lose detail in the coarse 7×7 visual grid, one of the reasons LayoutLMv3 moved to finer image patches.

6The same thing in Python

# pip install transformers pytesseract  (+ detectron2 for the LayoutLMv2 visual backbone)
from PIL import Image
from transformers import LayoutLMv2Processor, LayoutLMv2ForTokenClassification

processor = LayoutLMv2Processor.from_pretrained("microsoft/layoutlmv2-base-uncased")   # runs Tesseract OCR for you
labels = ["O", "B-COMPANY", "I-COMPANY", "B-DATE", "B-TOTAL", "I-TOTAL"]
model = LayoutLMv2ForTokenClassification.from_pretrained(
    "microsoft/layoutlmv2-base-uncased", num_labels=len(labels))     # fine-tune before use

page = Image.open("receipt.png").convert("RGB")
enc = processor(page, return_tensors="pt", truncation=True)
# enc["input_ids"]: word pieces;  enc["bbox"]: one 0-1000 box per piece;  enc["image"]: 224x224 page
logits = model(**enc).logits                    # (1, tokens, num_labels)
pred = [labels[i] for i in logits.argmax(-1)[0].tolist()]

# bring your own OCR: pass words and boxes (already scaled to 0-1000)
proc2 = LayoutLMv2Processor.from_pretrained("microsoft/layoutlmv2-base-uncased", apply_ocr=False)
enc2 = proc2(page, ["TOTAL", "13.55"], boxes=[[67, 710, 205, 743], [790, 710, 933, 743]], return_tensors="pt")
