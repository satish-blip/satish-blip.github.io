LLM pre-training: predict the next token, a trillion times

Every large language model starts the same way. Take a transformer with random weights, show it an enormous amount of text, and ask it again and again to guess the next token. That one dull task, done at a scale that costs millions of dollars, is where the model's knowledge of language, facts and reasoning comes from. This page trains a tiny next-character model in your browser, counts the compute a real run needs, and works through the scaling laws that tell labs how big a model to train and on how much data.

What is pre-training, in plain words?

The problem

We want one model that can write, summarise, translate, answer questions and write code. Labelled data for each of those jobs is scarce and expensive. Plain text, on the other hand, is everywhere: the web, books, papers, code. How do we learn from text that nobody has labelled?

The idea

Make the text label itself. In “The cat sat on the ___”, the next word is the answer, and it is already in the data. Next-token prediction turns every position of every document into a training example. A model that gets very good at it has to learn grammar, facts (“Paris is the capital of ___”), and some reasoning (“3 + 4 = ___”). This first, most expensive stage is pre-training; the result is a base model.

How it works

  1. Collect, clean and de-duplicate trillions of tokens of text and code.
  2. Pick a model size \(N\) and a data budget \(D\) using a scaling law.
  3. Train a decoder-only transformer to minimise cross-entropy on the next token, for weeks, on thousands of GPUs.
  4. Hand the base model to post-training, which turns it into an assistant.

An everyday picture

A child who has read every book in a huge library, with one rule: before turning each page, guess the first word on it. Nobody explains grammar or history; the guessing game alone forces the child to absorb both. The child ends up knowing a lot, but has never been taught to answer a question politely. That comes later.

Good at
  • Uses unlabelled data, of which there is a vast amount
  • One objective, many skills: knowledge, syntax, code, translation
  • Predictable: loss falls smoothly as a power law in size, data and compute
Watch out for
  • Enormously expensive, and mistakes are found only after weeks
  • The model absorbs the biases and errors in its data
  • A base model continues text; it does not follow instructions

1Next-token prediction, live

A character-level n-gram model learns from 85% of the sentences of a small corpus (a short story plus simple sentences) and is scored on the other 15%. Move the sliders: how much text it sees, and how many previous characters it may look at.

Each curve is one context length. Lower is better; the dashed line is a model that guesses uniformly among all characters. Generation backs off to a shorter context when the current one was never seen. Real LLMs do the same thing with ~100k-token vocabularies, thousands of tokens of context and a transformer in place of the count table.

Write a document as a sequence of tokens \(x_1,x_2,\dots,x_T\). By the chain rule of probability, the probability of the whole document factorises into one prediction per position:

$$p_\theta(x_1,\dots,x_T)=\prod_{t=1}^{T}p_\theta\big(x_t\mid x_{<t}\big).$$

So a model of “what comes next” is automatically a model of text. How do we choose the parameters \(\theta\)? By maximum likelihood: make the real documents as probable as possible. Taking minus the log and averaging over all \(T\) positions gives the pre-training loss, the average cross-entropy:

$$\mathcal L(\theta)=-\frac1T\sum_{t=1}^{T}\log p_\theta\big(x_t\mid x_{<t}\big).$$

Each term says: how surprised was the model by the token that actually came next? A model that put probability 0.5 on the right token pays \(\log 2\approx0.69\) nats (1 bit); one that put 0.01 pays 4.6 nats. \(e^{\mathcal L}\) is the perplexity, the effective number of tokens the model is choosing between.

The lab uses the simplest possible model: count how often each character followed each context of length \(k\) in the training text, and predict with those counts (plus a little smoothing so nothing has probability zero). Three lessons carry over directly to real LLMs:

  • More data lowers the loss, and with diminishing returns: each doubling of the text buys a smaller drop.
  • A bigger model needs more data. With \(k=5\) the model has far more “parameters” (one count per context) than \(k=1\). On little data it is worse than the small model, because most contexts were never seen; on more data it overtakes. That crossing is the scaling-law story of section 4 in miniature.
  • The samples get better as the loss falls. At \(k=0\) the text is letter soup with the right letter frequencies; at \(k=3\) real words appear. A transformer replaces the count table with a network that shares strength between similar contexts, so it can use thousands of tokens of context without having seen each one.
Algorithm: pre-training a language model
  1. input token stream from the corpus, model \(p_\theta\), context length \(n\), batch size \(B\)
  2. repeat until the token budget \(D\) is used
  3. cut \(B\) windows of \(n+1\) tokens from the stream
  4. inputs \(\leftarrow\) tokens \(1..n\); targets \(\leftarrow\) tokens \(2..n{+}1\) shift by one
  5. one forward pass gives \(p_\theta(\cdot\mid x_{<t})\) at every position causal mask
  6. \(\mathcal L\leftarrow\) mean of \(-\log p_\theta(\text{target}_t)\) over all \(B\cdot n\) positions
  7. \(\theta\leftarrow\) AdamW step on \(\nabla_\theta\mathcal L\), with warm-up and decaying learning rate
  8. return the base model \(p_\theta\)
Going deeper: why one forward pass trains on every position at once

A recurrent network must read token 1 before token 2. A transformer with a causal mask computes the prediction for every position in parallel, each one allowed to look only at earlier tokens. A window of 4,096 tokens therefore yields 4,096 training examples from a single pass. This parallelism, more than anything else, is why transformers replaced RNNs for pre-training.

Cross-entropy also has a floor. Text contains genuine randomness (which of several equally good words a writer picks), so even a perfect model has loss equal to the entropy of language. Scaling laws model this floor as the constant \(E\) in section 4.

2What goes in: the pre-training data

The objective is simple; the data is where most of the craft lies. A modern pre-training corpus is built in stages:

  1. Collect. Web crawls (Common Crawl), books, Wikipedia, scientific papers, code from public repositories, maths, conversations, and increasingly text in many languages.
  2. Extract and filter. Strip HTML, drop pages in the wrong language, and remove spam, boilerplate and toxic content with heuristics and small quality classifiers.
  3. De-duplicate. The web repeats itself: licences, templates, mirrored pages. Exact and near-duplicate removal (MinHash) makes training more efficient and reduces memorisation of repeated text.
  4. Decontaminate. Remove copies of benchmark test sets, or scores become meaningless (see leakage and contamination).
  5. Tokenise and mix. Convert to tokens with a BPE tokeniser and decide the data mixture: how often each source is sampled.

Mixture weights matter because sources differ in quality and size. Small, high-quality sources (Wikipedia, books) are often seen more than once, while the web is seen less than once.

For a concrete example, here is the published mixture of the first LLaMA models (1.4 trillion tokens):

Why “tokens” and not “words”? The model reads tokens from a fixed vocabulary of sub-word pieces (often 32k to 200k of them). In English one token is about ¾ of a word, so 1 trillion tokens is roughly 750 billion words.

3Counting the compute: C ≈ 6ND

Pick a famous model or set your own size and data. The calculator counts the floating-point operations, the GPU time, and the memory just to hold the training state.

Dense bf16 peak figures without sparsity. Real runs also lose time to failures and restarts, so treat the days as a lower bound.

How much arithmetic does training take? Count it for one token passing through a network with \(N\) weights. In the forward pass each weight is used in one multiply and one add: about \(2N\) FLOPs. The backward pass needs the gradient with respect to the activations and with respect to the weights, each costing about as much as the forward pass: another \(4N\). Over \(D\) training tokens,

$$C\;\approx\;6\,N\,D\ \text{FLOPs}.$$

Check it on GPT-3: \(6\times175\times10^{9}\times300\times10^{9}=3.15\times10^{23}\) FLOPs, which is the figure in the GPT-3 paper. Attention adds a term that grows with context length, but for large models at typical context lengths it is small, and the rule of thumb holds.

Wall-clock time is compute divided by throughput:

$$\text{time}=\frac{C}{\#\text{GPUs}\times\text{peak FLOP/s}\times\text{MFU}} .$$

The model FLOPs utilisation (MFU) is the share of the hardware's peak that does useful work; 35–50% is good for large runs, because GPUs also wait for memory and for each other.

Memory is the other wall. With mixed-precision AdamW, each parameter needs about 16 bytes: 2 for the bf16 weight, 2 for its gradient, and 12 for the fp32 master copy and Adam's two moment estimates. A 70B model therefore needs about 1.1 TB just for this state, more than ten 80 GB GPUs, before counting activations. That is why training is spread across GPUs with data, tensor, pipeline and sharded (ZeRO/FSDP) parallelism.

Going deeper: where the 6 comes from, layer by layer

For a linear layer \(y=Wx\) with \(W\in\mathbb R^{m\times n}\): the forward pass is \(mn\) multiply-adds, 2 FLOPs each, so \(2mn\). The backward pass computes \(\partial L/\partial x=W^\top g\) (another \(2mn\)) and \(\partial L/\partial W=g\,x^\top\) (another \(2mn\)). Total \(6mn\) per token, and summing over layers gives \(6N\). Kaplan et al. add the attention scores, \(2\,n_{\text{layer}}\,n_{\text{ctx}}\,d\) per token forward, which matters only when the context is long compared with the model width.

4Scaling laws: how big, on how much data?

The Chinchilla scaling law predicts the final loss from model size \(N\) and tokens \(D\). Fix a compute budget: every point on a curve costs the same, trading parameters for data. Where is the bottom?

Curves are isoFLOP profiles at C/10, C and 10C. Dots mark each curve's minimum. The table puts real models at their own compute and compares them with the compute-optimal choice.

In 2020 Kaplan et al. found that the loss of a language model falls as a power law in parameters, data and compute, over many orders of magnitude, and barely depends on details such as depth versus width. That made LLM training predictable: train small models, fit the curve, and extrapolate to a run that costs a thousand times more.

Hoffmann et al. (2022) trained over 400 models and fitted a law in both \(N\) and \(D\):

$$L(N,D)=E+\frac{A}{N^{\alpha}}+\frac{B}{D^{\beta}},\qquad E=1.69,\;A=406.4,\;B=410.7,\;\alpha=0.34,\;\beta=0.28 .$$

Read it term by term. \(E\) is the irreducible loss, the entropy of text itself. \(A/N^\alpha\) is the penalty for a model too small to represent the patterns; \(B/D^\beta\) is the penalty for having seen too little data. Now pose the question a lab faces: with a fixed budget \(C=6ND\), which \(N\) minimises the loss? Substitute \(D=C/(6N)\):

$$L(N)=E+A\,N^{-\alpha}+B\Big(\frac{6N}{C}\Big)^{\beta}.$$

The first term falls with \(N\), the second rises, so there is a minimum. Setting \(dL/dN=0\) gives \(\alpha A N^{-\alpha}=\beta B\,(6N/C)^{\beta}\), whose solution is

$$N_{\text{opt}}=G\Big(\frac{C}{6}\Big)^{\frac{\beta}{\alpha+\beta}},\quad D_{\text{opt}}=G^{-1}\Big(\frac{C}{6}\Big)^{\frac{\alpha}{\alpha+\beta}},\quad G=\Big(\frac{\alpha A}{\beta B}\Big)^{\frac{1}{\alpha+\beta}} .$$

Since the exponents are both close to \(\tfrac12\), parameters and data should grow in roughly equal proportion with compute. The paper's headline rule of thumb, from its two other estimation methods, is about 20 tokens per parameter. (The published constants above give noticeably more tokens per parameter than that; a 2024 replication found the fit itself was off, and its refit, the lab's default, agrees with about 20. Switch between them to see the difference.) GPT-3 and Gopher had used under 2: far too large for their data. To prove it, DeepMind trained Chinchilla with the same compute as the 280B-parameter Gopher but as a 70B model on 1.4T tokens, and it beat Gopher on nearly every benchmark while being four times cheaper to run.

Algorithm: choosing a compute-optimal model size (isoFLOP method)
  1. for each of several small budgets \(C_i\) do
  2. train models of 6–10 sizes \(N\), each on \(D=C_i/6N\) tokens
  3. fit a parabola to final loss against \(\log N\); record its minimum \(N^*_i\)
  4. fit a straight line \(\log N^*=a\log C+b\) through the points \((C_i,N^*_i)\)
  5. extrapolate to the real budget \(C\): \(N^*=10^{b}C^{a}\), \(D^*=C/6N^*\)
  6. return \(N^*, D^*\) Chinchilla found a ≈ 0.5
Going deeper: Kaplan vs Chinchilla, the 2024 refit, and why Llama is “over-trained”

Why did Kaplan et al. get a different answer? They concluded that \(N\) should grow faster than \(D\) (\(N_{\text{opt}}\propto C^{0.73}\)), which is why GPT-3 was so large. Hoffmann et al. traced the difference to using one learning-rate schedule length for all runs and to small models; with a cosine schedule matched to each run's length, the optimum moves to \(a\approx0.5\).

The refit. Besiroglu et al. (2024) reconstructed the Chinchilla data from the paper's figure and refitted the parametric law, getting \(E=1.82, A=482, B=2085, \alpha=0.35, \beta=0.37\). The published fit implied implausibly narrow confidence intervals and a different optimum from the paper's other methods; the refit's optimum is again close to 20 tokens per parameter, so the three methods agree.

Inference changes the answer. Compute-optimal minimises training cost for a given loss. A model that will serve billions of requests should be smaller and trained longer, because every request pays for every parameter. Llama 3 8B saw about 15T tokens, roughly 1,900 per parameter, nearly a hundred times past the Chinchilla point, and its loss was still falling.

Adapted from: Kaplan et al., Scaling Laws for Neural Language Models (2020); Hoffmann et al., Training Compute-Optimal Large Language Models (2022), equation 10 and its fitted constants; Besiroglu et al., Chinchilla Scaling: A replication attempt (2024).

5Emergent abilities: sudden, or a trick of the metric?

A model's chance of getting each token of an answer right improves smoothly with compute. Score it by exact match on a \(k\)-token answer and watch what happens to the curve.

Wei et al. (2022) collected tasks, such as multi-digit arithmetic, where small models score near zero and then, past some scale, accuracy jumps. They called these emergent abilities: abilities that are not present in smaller models and cannot be predicted by extrapolating them.

Schaeffer et al. (2023) offered a simpler explanation for many of them. Suppose the per-token accuracy \(p\) improves smoothly with compute. An answer of \(k\) tokens is exactly right only if every token is right, so

$$\text{exact match}=p^{k}.$$

With \(k=10\), going from \(p=0.6\) to \(p=0.9\) moves exact match from 0.6% to 35%: a sharp “emergence” built from a smooth improvement. Score the same models with a continuous metric (per-token accuracy, or the log-probability of the right answer) and the jump disappears. Switch the lab to a log axis and the exact-match curve, too, rises steadily.

This does not mean nothing new ever appears with scale; some abilities, such as following instructions in a prompt, really do become usable only above a size. The lesson is to look at continuous metrics before calling a capability unpredictable, and to remember that users experience the sharp, all-or-nothing version.

Adapted from: Wei et al., Emergent Abilities of Large Language Models (2022); Schaeffer, Miranda and Koyejo, Are Emergent Abilities of Large Language Models a Mirage? (NeurIPS 2023).

6The same thing in Python

The pre-training step in PyTorch for any decoder-only model, then the Chinchilla allocation as a function.

# pip install torch transformers
import math, torch, torch.nn.functional as F
from transformers import AutoConfig, AutoModelForCausalLM

# a small GPT-style model with random weights (pre-training starts from scratch)
cfg = AutoConfig.from_pretrained("gpt2", n_layer=6, n_head=8, n_embd=512)
model = AutoModelForCausalLM.from_config(cfg).cuda()
opt = torch.optim.AdamW(model.parameters(), lr=6e-4, betas=(0.9, 0.95), weight_decay=0.1)

def lr_at(step, warmup=1000, total=100_000, peak=6e-4):
    if step < warmup:                       # linear warm-up
        return peak * step / warmup
    t = (step - warmup) / (total - warmup)  # cosine decay to 10%
    return peak * (0.1 + 0.45 * (1 + math.cos(math.pi * t)))

def train_step(step, tokens):              # tokens: LongTensor [B, n+1] cut from the stream
    x, y = tokens[:, :-1], tokens[:, 1:]    # targets are the inputs shifted by one
    with torch.autocast("cuda", dtype=torch.bfloat16):
        logits = model(input_ids=x).logits  # [B, n, vocab], causal mask is built in
        loss = F.cross_entropy(logits.reshape(-1, logits.size(-1)), y.reshape(-1))
    loss.backward()
    torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    for g in opt.param_groups:
        g["lr"] = lr_at(step)
    opt.step(); opt.zero_grad(set_to_none=True)
    return loss.item()                      # perplexity = exp(loss)

# Chinchilla: compute-optimal N and D for a budget C (Hoffmann et al. 2022, eq. 10 fit)
def chinchilla(C, E=1.69, A=406.4, B=410.7, a=0.34, b=0.28):
    G = (a * A / (b * B)) ** (1 / (a + b))
    N = G * (C / 6) ** (b / (a + b))
    D = C / (6 * N)
    return N, D, E + A / N**a + B / D**b

N, D, L = chinchilla(5.76e23)               # Gopher's budget
print(f"N = {N/1e9:.0f}B params, D = {D/1e12:.2f}T tokens, {D/N:.0f} tokens/param, loss {L:.3f}")

For real runs, libraries such as Megatron-LM, torchtitan or Hugging Face nanotron add the parallelism, checkpointing and data loading. Karpathy's nanoGPT is the clearest small reference implementation.
