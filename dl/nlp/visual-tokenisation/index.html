Visual tokenisation: turning a picture into words

A transformer reads a list of vectors. For text, the tokeniser cuts the sentence into pieces and looks each one up. To let the same machinery read an image, we need the visual version of that step: cut the picture into pieces, and turn each piece into a vector. There are three main ways to do it, and this page lets you try all three.

What is visual tokenisation, in plain words?

The problem

A 224 × 224 colour photo is 150,528 numbers. A sentence is a handful of tokens. If we want one model to read both (to answer "what colour is the bus?", or to write a caption), the image has to arrive in the same form as the text: a short sequence of vectors, each standing for a meaningful piece. Feeding every pixel as its own token would give 50,176 tokens, and self-attention over them would need 2.5 billion scores per layer. We need a way to group pixels into a few hundred pieces that still carry what matters.

The idea

A visual token is one vector that stands for a piece of an image. The piece can be a fixed square patch (the vision transformer), a box around a detected object (region features), or a patch replaced by the id of its nearest entry in a learned codebook, which makes images look exactly like text: a list of integers from a fixed vocabulary.

How it works

  1. Choose the pieces: a grid of patches, or detected object boxes.
  2. Turn each piece into a vector: a linear projection of its pixels, or a detector's feature for the box.
  3. Add where the piece came from: a position embedding (or the box coordinates).
  4. Optionally snap each vector to its nearest codebook entry, giving a discrete id.

An everyday picture

Describing a photo over the phone. You might go square by square ("top left is sky, next to it more sky, then the sun"), or object by object ("a dog, a red ball, a tree"), or with a fixed set of agreed words ("blue, blue, yellow, green"). Those are patches, regions and codebook tokens.

Good at
  • Lets one transformer read text and images together
  • Patches need no extra model and cover every pixel
  • Codebook tokens let a language model also write images
Watch out for
  • Small patches mean many tokens and quadratic attention cost
  • Region detectors miss things they were not trained on
  • Quantising throws away detail

1Patches: cut the picture into a grid

The simplest visual tokeniser does not look at the content at all: it cuts the image into equal squares and reads them left to right, top to bottom, like words on a page. Pick a scene and a patch size, then tap any patch to find it in the sequence.

The image as a sequence

The first tile is the [CLS] token, a learned extra token whose output will summarise the whole picture. Every other tile is one patch, in raster order.

Counting tokens. An image of \(H\times W\) pixels cut into \(P\times P\) patches gives \(N=\frac{H}{P}\cdot\frac{W}{P}\) tokens. The standard ViT-B/16 uses \(224\times224\) images and \(P=16\), so \(N=14\times14=196\) tokens, each made of \(16\cdot16\cdot3=768\) numbers. Halve the patch size and you get four times as many tokens and sixteen times as many attention scores, because attention compares every token with every other one (\(N^2\)).

2From patch to vector: the vision transformer

A patch is still just pixels. The vision transformer (ViT) flattens each one into a long vector and multiplies it by one learned matrix \(E\), the same for every patch, exactly as a word is looked up in an embedding table. Then it adds a position embedding so the model knows where the patch was, and hands the sequence to an ordinary transformer.

Step by step

Flatten. Patch \(p\) becomes \(x_p\in\mathbb R^{P^2C}\): its \(P\times P\) pixels, each with \(C=3\) colour values, in a row.

Project. One shared linear map gives the patch embedding \(Ex_p\in\mathbb R^{D}\), with \(E\) of shape \(D\times P^2C\). This is the visual analogue of a token embedding. In code it is a convolution with kernel size and stride both equal to \(P\).

Add position. Attention ignores order, so each grid position gets a learned vector \(e^{\text{pos}}_p\). Without it, a shuffled image would look identical to the model.

$$z_0=\big[\,x_{\text{cls}};\;Ex_1;\;Ex_2;\;\dots;\;Ex_N\,\big]+E_{\text{pos}}$$

Transform. \(z_0\) goes through \(L\) standard transformer blocks (the same ones as on the transformers page). The output above \(x_{\text{cls}}\) is the image's summary vector; a linear layer on it gives class scores, or it becomes the image embedding in a multimodal model.

Your selected patch, as numbers

Here the projection is hand-made so you can read it: 8 numbers per patch that measure colour, brightness, contrast and edges. A trained ViT learns \(D=768\) such directions by itself. "Similarity" colours every patch by the cosine similarity of its vector to the selected one: patches of sky find other sky, patches of grass find grass.

Algorithm: ViT patch tokenisation
  1. input image \(I\) (\(H\times W\times C\)), patch size \(P\), projection \(E\) (\(D\times P^2C\)), position table \(E_{\text{pos}}\)
  2. cut \(I\) into \(N=HW/P^2\) patches, row by row raster order, like reading a page
  3. for each patch \(p=1..N\) do
  4. \(x_p\leftarrow\) flatten the patch to \(P^2C\) numbers
  5. \(t_p\leftarrow Ex_p\) same E for every patch
  6. \(t_p\leftarrow t_p+E_{\text{pos}}[p]\) remember where it came from
  7. prepend the learned \(x_{\text{cls}}\) its output summarises the image
  8. return the \(N+1\) tokens to the transformer
Going deeper: why one linear map is enough, and what ViT gives up

The projection is linear, so on its own it can only detect patterns that are weighted sums of pixels (a colour, an edge at a fixed place). That is enough because everything clever happens later: the first attention layer already lets each patch look at every other patch in the image, something a convolutional network only achieves after many layers. Visualising the learned rows of \(E\) shows smooth colour blobs and edge detectors, very like the first layer of a CNN.

The price is inductive bias. A CNN is built to assume that nearby pixels belong together and that a cat is a cat wherever it appears. ViT only has the patch grid; it must learn locality from data. That is why the original ViT lost to ResNets when trained on ImageNet alone (1.3 M images) and won only after pre-training on 300 M images. Data-efficient tricks (DeiT: strong augmentation and distillation) and hybrid designs (a CNN stem, or Swin's windowed attention) narrow the gap.

Resolution. The position table is learned for one grid size. To run on larger images, ViT keeps \(P\) fixed (so it gets more tokens) and interpolates \(E_{\text{pos}}\) in 2-D to the new grid.

3Object regions: tokens that are already things

Before ViT, vision-and-language models (VisualBERT, ViLBERT, LXMERT, UNITER) used an object detector as their tokeniser. A Faster R-CNN finds boxes around objects, and each box becomes one token: a feature vector for what is inside it, plus where the box is. Compare the two kinds of tokens on the same scene.

Region tokens

Each token here is the box's average colour (4 numbers) followed by its geometry: left, top, right, bottom and area as fractions of the image (5 numbers). A real detector gives 2,048 learned numbers per box instead of the colour, and the same 5 geometry numbers.

Why it was popular. A region token already means something: "dog", "ball". Captions mention objects, so linking words to regions is easy to learn. Ten to a hundred boxes are also far fewer tokens than hundreds of patches.

Why it faded. The detector is a separate, frozen model trained on a fixed list of object classes (Visual Genome's 1,600). Anything it does not know (a logo, text in the image, the sky, the spatial layout between boxes) is partly lost, it is slow, and the whole system cannot be trained end to end. Patch-based encoders such as CLIP's ViT replaced it from about 2021.

Going deeper: how a detector turns a box into a vector (RoI pooling)

Faster R-CNN first runs a CNN (for example ResNet-101) over the whole image, giving a feature map that is about 1/16 of the image size with 1,024 or 2,048 channels. A small region proposal network slides over this map and proposes boxes that probably contain an object. For each kept box, RoI pooling (or RoIAlign) cuts the box out of the feature map and resamples it to a fixed \(7\times7\) grid, whatever the box's size; a few more layers and an average give one fixed-length vector per box. That vector, plus the box coordinates, is the region token.

Because every box goes through the same pooling, a tiny ball and a huge tree both become vectors of the same length, which is exactly what a transformer needs.

4A codebook of visual words

Patches and regions give continuous vectors. Text tokens are integers from a fixed vocabulary. Vector quantisation closes the gap: learn \(K\) prototype vectors (the codebook) and replace every patch by the id of the closest one. Now an image is a list of integers, and a language model can read and even generate it. Drag \(K\) and watch the image rebuilt from its tokens.

The codebook

The image, as token ids

Here each patch (12 × 12 pixels, 256 patches) is described by its average colour, and the codebook is found with k-means. Real image tokenisers (VQ-VAE, VQGAN, DALL-E's dVAE) quantise learned feature vectors instead, with \(K=8{,}192\) or more, and train a decoder that redraws fine detail from the ids.

Algorithm: vector-quantising image patches into a codebook
  1. input patch vectors \(z_1..z_N\) from many images, codebook size \(K\)
  2. pick \(K\) starting codes \(c_1..c_K\) e.g. random patches
  3. repeat
  4. for each patch: \(\text{id}_i\leftarrow\arg\min_k\lVert z_i-c_k\rVert^2\) nearest code
  5. for each code: \(c_k\leftarrow\) mean of the patches assigned to it
  6. until the assignments stop changing
  7. to tokenise an image: replace each patch by its \(\text{id}\) a list of integers
  8. to decode: look up \(c_{\text{id}}\) for each token and redraw the patch
Going deeper: VQ-VAE, and passing gradients through argmin

In a VQ-VAE the patch vectors \(z_e(x)\) come from a trainable encoder, the quantised vectors \(z_q=c_{\text{id}}\) go into a trainable decoder, and the codebook itself is learned. The loss has three parts:

$$\mathcal L=\lVert x-\hat x\rVert^2+\lVert\operatorname{sg}[z_e]-c\rVert^2+\beta\,\lVert z_e-\operatorname{sg}[c]\rVert^2$$

The first term rebuilds the image. The second pulls each used code toward the encoder outputs assigned to it (this is the k-means step above, done by gradient descent). The third, the commitment loss with \(\beta\approx0.25\), stops the encoder outputs drifting away from the codes. \(\operatorname{sg}\) means stop-gradient: treat it as a constant.

The argmin has no useful gradient, so the encoder is trained with the straight-through estimator: in the backward pass, copy the gradient arriving at \(z_q\) directly to \(z_e\), as if quantisation were the identity. DALL-E's dVAE uses a Gumbel-softmax relaxation instead. Either way, once trained, a transformer can model images as sequences of ids with the same next-token loss used for text.

6The same thing in Python

import torch, torch.nn as nn
img = torch.randn(1, 3, 224, 224)                  # batch, channels, height, width
P, D = 16, 768
patchify = nn.Conv2d(3, D, kernel_size=P, stride=P)       # = one shared linear map E per patch
tok = patchify(img).flatten(2).transpose(1, 2)       # (1, 196, 768): 14 x 14 patches
cls = nn.Parameter(torch.zeros(1, 1, D))
pos = nn.Parameter(torch.zeros(1, 197, D))
z0 = torch.cat([cls, tok], dim=1) + pos                 # (1, 197, 768) -> transformer

# a pre-trained ViT from Hugging Face
from transformers import ViTImageProcessor, ViTModel
proc  = ViTImageProcessor.from_pretrained("google/vit-base-patch16-224")
model = ViTModel.from_pretrained("google/vit-base-patch16-224")
# out = model(**proc(images=pil_image, return_tensors="pt"))
# out.last_hidden_state: (1, 197, 768); [:, 0] is the [CLS] summary

# vector quantisation: nearest code for each patch vector
codebook = torch.randn(8192, D)
ids = torch.cdist(tok[0], codebook).argmin(dim=1)      # (196,) integers, like word ids
