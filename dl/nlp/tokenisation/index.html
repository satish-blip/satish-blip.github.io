Tokenisation: text to numbers

A neural network only understands numbers. Before a model can read a sentence, the sentence is cut into pieces called tokens, and each piece is replaced by its id in a fixed vocabulary. How you cut matters: it decides what the model can see, how long its inputs are, and which words it can never spell.

What is tokenisation, in plain words?

The problem

A model needs a fixed list of symbols it knows. Use whole words and the list is huge, yet a new word like "unfriendable" or a typo is still unknown. Use single characters and nothing is ever unknown, but every sentence becomes very long and each symbol carries almost no meaning. We want a middle ground, learned from data: common words stay whole, rare words are spelled out from reusable pieces.

The idea

A neural network can only do arithmetic, so text must first become numbers. Tokenisation cuts text into pieces called tokens and gives each piece an id from a fixed vocabulary. Whole words make the vocabulary huge and leave unknown words (out of vocabulary); single characters make sequences very long. Modern models use subwords: common words stay whole, rare words split into reusable parts.

How it works

  1. Pick a unit: word, character, byte or subword.
  2. For subwords, learn merges from a corpus: BPE repeatedly glues the most frequent neighbouring pair; WordPiece picks the pair that most raises likelihood.
  3. Apply the learned rules to new text to get a list of ids.
  4. The model only ever sees those ids.

An everyday picture

Like Lego: a small box of standard bricks can build any model. "unbelievable" becomes "un" + "believ" + "able", pieces that also appear in hundreds of other words.

Good at
  • Any text can be encoded, nothing is unknown
  • Common words cost one token
  • Vocabulary size is a dial you control
Watch out for
  • Rare words and other languages cost more tokens
  • Numbers and spelling get split oddly
  • Tokeniser choices are fixed once the model is trained

2Byte-pair encoding, step by step

BPE (Sennrich et al. 2016, used by GPT models) builds a subword vocabulary bottom-up:

  1. Start with every word split into characters. Mark the start of a word with ▁ so "learn" at the start of a word differs from "learn" inside one.
  2. Count every pair of neighbouring symbols, weighted by how often each word occurs.
  3. Merge the most frequent pair into one new symbol, add it to the vocabulary, and rewrite every word.
  4. Repeat until the vocabulary is as big as you want.

To tokenise new text, apply the learned merges in the same order. Frequent words end up as a single token; rare words fall apart into familiar pieces, so nothing is ever truly unknown.

Algorithm: byte-pair encoding (training)
  1. input a corpus of words with their counts, a target vocabulary size \(V\)
  2. split every word into characters (plus an end-of-word mark); vocabulary \(\leftarrow\) all characters
  3. while vocabulary size \(<V\) do
  4. count every adjacent pair of symbols, weighted by word count e.g. (l, o) appears 12 times
  5. pick the most frequent pair \((a,b)\)
  6. replace every \(a\;b\) by the new symbol \(ab\) in all words merge
  7. add \(ab\) to the vocabulary; append the rule \(a+b\to ab\) to the merge list
  8. return the vocabulary and the ordered merge list to tokenise new text, replay the merges in order
Going deeper: why BPE is a compression algorithm, and byte-level BPE

BPE began life in 1994 as a data compression method: repeatedly replace the most common pair of bytes with a new unused byte. Each merge shortens the corpus by exactly the number of times the pair occurs, so BPE is a greedy algorithm that, at every step, makes the biggest possible cut in total length. It is not guaranteed to find the best vocabulary of size \(V\) (that problem is hard), but greedy works well in practice.

Byte-level BPE (GPT-2 onwards) starts from the 256 possible bytes instead of characters. Since every piece of text in any language, including emoji, is a sequence of bytes, nothing can ever be unknown. WordPiece (BERT) picks the pair that most increases the likelihood of the corpus, \(\text{count}(ab)/(\text{count}(a)\,\text{count}(b))\), instead of the raw count, which favours pairs that stick together more than chance predicts. Unigram (SentencePiece) runs the other way: start large and prune the pieces whose removal hurts the likelihood least.

3The trade-off: vocabulary size versus sequence length

As BPE merges more pairs, the vocabulary grows (x-axis) and the average number of tokens per word on the corpus falls (y-axis). The dot is the current merge count from section 2.

Characters give a tiny vocabulary but very long sequences: the model must learn spelling and needs many steps per sentence (and attention cost grows with the square of the length). Whole words give short sequences but a huge vocabulary, a giant embedding table, and no way to handle new words.

Subwords sit in between. Real models use roughly:

BERTWordPiece30,522
GPT-2byte-level BPE50,257

GPT-4o, LLaMA 3byte-level BPE~128k to 200k

English averages about 0.75 words per token for these models, so 1,000 tokens is roughly 750 words.

4WordPiece: greedy longest match

WordPiece (used by BERT) builds a vocabulary much like BPE, but chooses the merge that most increases the likelihood of the training data, scoring a pair by \(\dfrac{\text{count}(ab)}{\text{count}(a)\,\text{count}(b)}\) rather than by raw frequency. Pieces that continue a word are written with ##.

To tokenise, it scans each word left to right and always takes the longest vocabulary piece that matches, then continues from where it stopped. If at some point nothing matches, the whole word becomes [UNK].

5Quirks that come from tokenisation

Spelling and counting

A model that sees "strawberry" as two or three tokens never directly sees its letters, which is why language models are bad at counting the r's or reversing words.

Numbers

"12345" may be split as "123" + "45" while "12346" splits differently, so arithmetic is harder than it should be. Some tokenisers split every digit separately for this reason.

Other languages

Tokenisers trained mostly on English need many more tokens for Hindi, Tamil or Thai text: the same sentence costs more, fits less in the context window, and the model sees it in smaller pieces. Byte-level BPE at least guarantees no [UNK].

Leading spaces

" the" and "the" are different tokens (GPT shows the space as Ġ, SentencePiece as ▁). A prompt ending in a space can change what comes next.

Special tokens

Tokens like [CLS], [SEP], [MASK], <|endoftext|> mark structure: the start of an input, a boundary between sentences, a hidden word, the end of a document.

Same text, different ids

Every model has its own vocabulary, so token ids (and token counts, and prices per token) are not comparable across models.

6The same thing in Python

from transformers import AutoTokenizer
bert = AutoTokenizer.from_pretrained("bert-base-uncased")      # WordPiece
gpt2 = AutoTokenizer.from_pretrained("gpt2")                   # byte-level BPE
bert.tokenize("Tokenisers learned unbelievably")   # ['token', '##isers', 'learned', 'un', '##bel', '##ie', '##va', '##bly']
gpt2("Hello world").input_ids                       # [15496, 995]

# train your own BPE
from tokenizers import Tokenizer, models, trainers, pre_tokenizers
tok = Tokenizer(models.BPE(unk_token="[UNK]")); tok.pre_tokenizer = pre_tokenizers.Whitespace()
tok.train(["corpus.txt"], trainers.BpeTrainer(vocab_size=8000, special_tokens=["[UNK]"]))
