Retrieval-augmented generation: look it up, then answer

A language model only knows what was in its training data, frozen at one date, and it cannot tell you where a fact came from. RAG fixes this with a search step: before answering, fetch the few passages most likely to help, put them in front of the model, and let it write an answer grounded in them. This page covers how that search works, the full pipeline, and three papers that shaped it.

What is RAG, in plain words?

The problem

A language model only knows what was in its training data, frozen at some date, and when it does not know something it may confidently make it up. Retraining it every time a document changes is far too expensive, and you cannot easily check where an answer came from. We want the model to look things up: find the relevant passages in a document collection at question time, read them, and answer from them.

The idea

Retrieval-augmented generation splits knowledge in two. The model’s weights hold language and reasoning (its parametric memory); a searchable store of documents holds the facts. A retriever picks the passages that match the question, and the generator writes the answer from them.

How it works

  1. Split documents into short chunks and index them (word counts, embeddings, or both).
  2. Turn the question into the same kind of representation and fetch the top \(k\) chunks.
  3. Put the question and the chunks into the model’s input.
  4. Generate an answer that uses, and ideally cites, those chunks.

An everyday picture

An open-book exam. A student who has learnt how to reason but cannot remember every date does well if the right page is open in front of them. Most of RAG’s quality comes from two things: finding the right page, and the student knowing which page to trust.

Good at
  • Up-to-date and private knowledge without retraining
  • Answers can cite their sources
  • Fewer hallucinations on factual questions
Watch out for
  • Bad retrieval means a confident wrong answer
  • Irrelevant passages can distract the model
  • Extra latency and an index to maintain

1Theory: sparse vs dense retrieval

Sparse: count the words

Represent each passage as a vector with one slot per word in the vocabulary, almost all zeros. A query scores a passage by the words they share, weighted so that rare words count more. The workhorse is BM25:

$$\text{BM25}(q,d)=\sum_{t\in q}\underbrace{\log\!\Big(1+\frac{N-n_t+0.5}{n_t+0.5}\Big)}_{\text{IDF: rare words matter}}\cdot\underbrace{\frac{f_{t,d}\,(k_1+1)}{f_{t,d}+k_1\big(1-b+b\,\frac{|d|}{\overline{|d|}}\big)}}_{\text{saturating count, length-normalised}}$$

\(N\) passages, \(n_t\) of them contain word \(t\), \(f_{t,d}\) is how often \(t\) appears in \(d\). \(k_1\approx1.2\) makes the tenth repeat of a word worth far less than the first; \(b\approx0.75\) stops long passages winning just by being long.

Logic: exact, explainable, no training, and an inverted index makes it fast. Weakness: the vocabulary mismatch problem: “car crash” scores zero against “automobile accident”.

Dense: compare meanings

A neural encoder maps text to a short dense vector (768 numbers in DPR). In a bi-encoder the query and passage are encoded separately and scored by a dot product:

$$s(q,d)=E_Q(q)^\top E_P(d),\qquad \mathcal L=-\log\frac{e^{s(q,d^+)}}{e^{s(q,d^+)}+\sum_{j}e^{s(q,d_j^-)}}$$

The encoders are trained with this contrastive loss: pull each question towards the passage that answers it (\(d^+\)) and away from the others in the batch (\(d^-_j\)). All passage vectors are computed once and stored; at query time, maximum inner product search over a FAISS index finds the top \(k\) in milliseconds.

Logic: paraphrases and synonyms land close together. Weakness: rare names, codes and exact phrases (a policy number, “attachment point”) can be blurred, and it needs training data and an embedding model.

2The full pipeline

A production RAG system has an offline half (build the index) and an online half (answer a question). Every box is a design choice that changes answer quality.

Offline
  1. LoadPDFs, web pages, tables
  2. Cleanstrip boilerplate, keep titles
  3. Chunk100–500 tokens, some overlap
  4. Embedencoder → vector per chunk
  5. IndexFAISS / BM25 / both, plus metadata
Online
  1. Queryrewrite or expand if needed
  2. Retrievetop 20–100, sparse + dense
  3. Re-rankcross-encoder keeps the best 3–10
  4. Promptquestion + passages + instructions to cite
  5. Generateanswer with citations
Evaluate
  1. Retrievalrecall@k, MRR
  2. Answerexact match, F1
  3. Faithfulnessis every claim supported?

Algorithm: retrieval-augmented generation
  1. offline: split documents into chunks; \(e_j\leftarrow\operatorname{Enc}_D(\text{chunk}_j)\); build an index done once
  2. input a question \(q\)
  3. \(e_q\leftarrow\operatorname{Enc}_Q(q)\) same vector space as the chunks
  4. for each chunk \(j\): \(s_j\leftarrow e_q^\top e_j\) in practice an approximate nearest-neighbour search
  5. \(Z\leftarrow\) the top-\(k\) chunks by score optionally re-rank with a cross-encoder
  6. prompt \(\leftarrow\) instructions + \(Z\) + \(q\)
  7. answer \(\leftarrow\operatorname{LLM}(\text{prompt})\) generated token by token, citing Z
  8. return the answer and its sources
Going deeper: RAG as a latent-variable model

The original RAG paper treats the retrieved passage \(z\) as a hidden variable and marginalises over it: \(p(y\mid q)\approx\sum_{z\in\text{top-}k}p_\eta(z\mid q)\,p_\theta(y\mid q,z)\), with \(p_\eta(z\mid q)\propto\exp(e_q^\top e_z)\). Because the sum is differentiable in the retriever scores, the question encoder can be trained end to end from answer quality alone, with no labels saying which passage was right. (The document encoder is kept frozen so the index does not need rebuilding.)

Practical systems often skip the marginalisation and simply paste the top-\(k\) chunks into the prompt, as in the algorithm above. The weak points are then visible in the algorithm itself: a bad chunking step splits the answer across chunks, the retriever misses it (recall@k), or the generator ignores or misreads the retrieved text (faithfulness). Evaluate each stage separately.

3Paper 1: RAG, the original (Lewis et al., NeurIPS 2020)

“Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks.” The paper that named the idea: a retriever and a generator trained together, end to end, with no label saying which passage is the right one.

Intuition

Treat the retrieved passage \(z\) as a hidden variable. We never know for sure which passage the answer came from, so we marginalise: average the generator’s answer over the top \(k\) passages, weighted by how relevant the retriever thinks each one is. Good passages then earn credit through the gradient, which teaches the retriever as well.

The pieces

  • Retriever \(p_\eta(z\mid x)\): DPR, two BERT-base encoders. Index: Wikipedia (December 2018) split into 100-word passages, 21 million of them, searched with FAISS (HNSW).
  • Generator \(p_\theta(y_i\mid x,z,y_{1:i-1})\): BART-large (about 400M parameters); the question and passage are simply concatenated as its input.
  • Training: minimise \(-\log p(y\mid x)\) summed over examples. Only the query encoder and BART are fine-tuned; the passage encoder and index stay frozen, because updating them would mean rebuilding a 21M-vector index.

The maths: two ways to marginalise

$$p_\eta(z\mid x)\;\propto\;\exp\!\big(\mathbf d(z)^\top\mathbf q(x)\big)$$

RAG-Sequence: one passage writes the whole answer; mix whole answers.

$$p(y\mid x)\approx\!\!\sum_{z\in\text{top-}k}\!\! p_\eta(z\mid x)\prod_{i=1}^{N}p_\theta(y_i\mid x,z,y_{1:i-1})$$

RAG-Token: each next token can lean on a different passage; mix at every step.

$$p(y\mid x)\approx\prod_{i=1}^{N}\;\sum_{z\in\text{top-}k}\! p_\eta(z\mid x)\,p_\theta(y_i\mid x,z,y_{1:i-1})$$

Logic: sum-then-multiply (Token) lets an answer combine facts from two passages; multiply-then-sum (Sequence) rewards one passage that explains everything. Decoding RAG-Sequence needs a beam search per passage (“Thorough”) or an approximation (“Fast”).

Try it: why the order of sum and product matters

Question: “Where and when did Hurricane Andrew make landfall?” Answer: two tokens, Florida then 1992. Passage A mentions Florida but not the year; passage B mentions 1992 but not the state.

4Paper 2: Fusion-in-Decoder (Izacard & Grave, EACL 2021)

“Leveraging Passage Retrieval with Generative Models for Open Domain Question Answering.” A very simple change to how the reader sees the passages, which lets it use 100 of them instead of a handful.

Intuition

Evidence for an answer is often scattered: one passage names the person, another gives the date. Reading more passages helps, but pasting 100 passages into one input makes self-attention cost explode. FiD’s answer: read each passage on its own, then think about all of them together.

Architecture

  1. Retrieve 100 passages (DPR for NaturalQuestions and TriviaQA, BM25 for SQuAD).
  2. For each passage build question: … title: … context: … and run the T5 encoder on it independently.
  3. Concatenate all the encoder outputs into one long sequence.
  4. The decoder’s cross-attention reads that whole sequence: evidence is fused in the decoder only.

The maths: why it scales

Self-attention over a sequence of length \(T\) costs about \(T^2\). With \(n\) passages of \(L\) tokens each:

$$\underbrace{(nL)^2}_{\text{one long input}}\quad\text{vs}\quad\underbrace{n\,L^2}_{\text{FiD encoder}}\;=\;\frac{1}{n}\times\text{the cost}$$

The encoder cost grows linearly in \(n\), not quadratically. The decoder still cross-attends to all \(nL\) vectors, but it only produces a short answer, so that part stays cheap.

Train with fewer passages? (dev EM, tested with 100)

Training on 5 passages and testing on 100 loses a lot (37.8 on NQ); 1,000 extra steps of fine-tuning with 100 passages recovers most of it (45.0), for a fraction of the GPU hours.

Limits: the retriever is fixed, not trained with the reader, and decoder cost still grows with the total number of passage tokens.

5Paper 3: RAFT (Zhang et al., 2024)

“RAFT: Adapting Language Model to Domain Specific RAG.” Instead of improving retrieval, teach the generator how to use what retrieval gives it, including the junk.

Intuition: studying for an open-book exam

Plain RAG is an open-book exam taken without studying: the model sees the pages but has never practised using them. Plain fine-tuning is studying without the book: it memorises answers but never learns to read sources. RAFT studies for the open-book exam: practise with the book open, including pages that look relevant but are not (distractors).

The training recipe

Each example has a question \(Q\), the golden document \(D^*\) that contains the answer, distractors \(D_1,\dots,D_k\), and a target answer \(A^*\):

$$\begin{aligned}P\%:&\quad Q + D^* + D_1 + \dots + D_k \;\to\; A^*\\(1-P)\%:&\quad Q + D_1 + \dots + D_k \;\to\; A^*\end{aligned}$$

The paper trains with the golden document plus 4 distractors. In \((1-P)\%\) of examples the golden document is missing, which pushes the model to also learn the domain knowledge itself rather than relying only on the context.

The answer is a cited chain of thought

\(A^*\) is not a bare answer. It is a chain of thought that quotes the golden document word for word and then concludes (the paper generated these with GPT-4):

##Reason: The document says ##begin_quote## Hurricane Andrew made landfall near Homestead, Florida on August 24, 1992 ##end_quote##, so the state is Florida.
##Answer: Florida

Logic: quoting forces the model to locate the evidence; reasoning over it stops the model latching on to a distractor that shares words with the question. The loss is ordinary next-token cross-entropy on \(A^*\); all the cleverness is in the data.

Answer metrics, with calculators

Exact match and token F1 (NQ, TriviaQA, WebQuestions, SQuAD)

Both answers are first normalised: lower-case, remove punctuation, drop the articles a / an / the, collapse spaces. Then

$$\text{EM}=\max_{g\in\text{gold}}\mathbb 1[\text{norm}(\hat y)=\text{norm}(g)]$$ $$P=\frac{|\hat y\cap g|}{|\hat y|},\;\;R=\frac{|\hat y\cap g|}{|g|},\;\;F_1=\frac{2PR}{P+R}$$

EM is all-or-nothing; F1 gives partial credit for overlapping words (counted as a multiset of tokens). Both take the best score over all accepted gold answers. The papers report EM averaged over the test set, as a percentage.

BLEU-1 and ROUGE-L (MS MARCO, Jeopardy)

For free-form answers exact match is too harsh, so we measure word overlap with a human reference.

$$\text{BLEU-1}=\text{BP}\cdot\frac{\sum_w\min\big(c_{\hat y}(w),\,c_{r}(w)\big)}{|\hat y|},\qquad \text{BP}=\begin{cases}1&|\hat y|>|r|\\ e^{\,1-|r|/|\hat y|}&\text{otherwise}\end{cases}$$

BLEU-1 is precision of single words, each word’s count clipped to how often it appears in the reference (so repeating “the” does not help), times a brevity penalty for answers that are too short.

$$P_{L}=\frac{\text{LCS}}{|\hat y|},\;\;R_{L}=\frac{\text{LCS}}{|r|},\;\;\text{ROUGE-L}=\frac{(1+\beta^2)P_LR_L}{R_L+\beta^2P_L}$$

ROUGE-L uses the longest common subsequence: words that appear in the same order, not necessarily next to each other. With \(\beta=1\) it is the F1 of the LCS; MS MARCO’s official script uses \(\beta=1.2\), which leans towards recall. Q-BLEU-1 (Jeopardy) is BLEU-1 re-weighted so that matching the named entities and question words counts more than matching filler words.

Accuracy (FEVER, PubMedQA, HotpotQA)

When the output is a label, or one short answer judged right or wrong, the metric is the share correct: \(\text{Acc}=\frac{\#\text{correct}}{\#\text{questions}}\). FEVER reports it two ways: 3-way (supports / refutes / not enough info) and 2-way (supports / refutes only). Worked example: 10 FEVER claims.

AST match (Gorilla APIBench, used by RAFT)

Code can be right with different spacing or argument order, so the generated call is parsed into a syntax tree and compared with the reference API: same function, and every argument the reference specifies must match. Extra optional arguments are allowed; a wrong model name or a call to an API that does not exist (a hallucination) fails.

Retrieval metrics, computed live on the search demo

Each preset question from section 1 has a passage we judge relevant. For a ranking, with \(\text{rank}_q\) the position of the first relevant passage:

$$\text{Recall@}k=\frac1{|Q|}\sum_{q}\mathbb 1[\text{rank}_q\le k],\qquad \text{MRR}=\frac1{|Q|}\sum_q\frac1{\text{rank}_q}$$

RAG and FiD report answer recall@k: is the gold answer string inside any of the top \(k\) passages? It is the same idea with “contains the answer” as the relevance test. FiD’s gains from 10 to 100 passages come from exactly this: recall keeps rising with \(k\). Move the BM25 and hybrid sliders in section 1 and the table updates.

8The same thing in Python

# pip install rank_bm25 sentence-transformers faiss-cpu
from rank_bm25 import BM25Okapi
from sentence_transformers import SentenceTransformer
import faiss, numpy as np

docs = ["Hurricane losses in Florida pushed reinsurance rates higher.",
        "Automobile accident frequency fell after speed limits were lowered."]
query = "car crash"

# sparse: BM25 over lower-cased word lists
bm25 = BM25Okapi([d.lower().split() for d in docs], k1=1.2, b=0.75)
sparse = bm25.get_scores(query.lower().split())

# dense: a bi-encoder + inner-product index (unit vectors, so this is cosine)
enc = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2")
D = enc.encode(docs, normalize_embeddings=True).astype("float32")
index = faiss.IndexFlatIP(D.shape[1]); index.add(D)
scores, ids = index.search(enc.encode([query], normalize_embeddings=True), k=2)

# hybrid: reciprocal rank fusion
def rrf(*rankings, c=60):
    s = {}
    for r in rankings:
        for rank, i in enumerate(r): s[i] = s.get(i, 0) + 1 / (c + rank + 1)
    return sorted(s, key=s.get, reverse=True)
top = rrf(list(np.argsort(-sparse)), list(ids[0]))

# the original RAG model (Lewis et al.) on Hugging Face
from transformers import RagTokenizer, RagRetriever, RagSequenceForGeneration
tok = RagTokenizer.from_pretrained("facebook/rag-sequence-nq")
ret = RagRetriever.from_pretrained("facebook/rag-sequence-nq", index_name="exact", use_dummy_dataset=True)
model = RagSequenceForGeneration.from_pretrained("facebook/rag-sequence-nq", retriever=ret)
out = model.generate(**tok("who holds the record in 100m freestyle", return_tensors="pt"))
print(tok.batch_decode(out, skip_special_tokens=True))

The dummy dataset keeps the download small, so its answers are not meaningful; use index_name="compressed" for the full Wikipedia index (tens of GB).
