LLM inference: making every generated token cheap

Training a model happens once; serving it happens billions of times. Generating text one token at a time turns out to be limited less by arithmetic than by how fast the GPU can read memory. This page works out where the time and memory go, then covers the tricks that every serving stack uses: the KV cache and grouped-query attention, batching, speculative decoding (which is provably exact), and quantising the weights to 4 bits with GPTQ, AWQ and llama.cpp's GGUF formats.

What makes LLM inference hard, in plain words?

The problem

A language model writes one token at a time, and each new token needs a full pass through the network: every one of its billions of weights read from memory, to produce a few bytes of output. Users want answers fast, providers want each GPU to serve many users, and many people want to run models on a laptop. How do we cut the cost of each token without changing the answers?

The idea

Avoid repeated work, move fewer bytes, and do more useful work per byte moved. The KV cache stores what earlier tokens computed so it is never recomputed. Batching shares each read of the weights among many users. Speculative decoding lets a small model guess several tokens that the big model checks in one pass. Quantisation stores weights in 4 or 8 bits so there is less to read.

How it works

  1. Prefill: read the whole prompt in one parallel pass and fill the KV cache.
  2. Decode: generate token by token, each step reading the weights and the cache.
  3. A scheduler batches many requests and manages cache memory in pages.
  4. Optional: a draft model proposes tokens; weights are 4–8-bit.

An everyday picture

A chef (the GPU) who must fetch a heavy recipe book from the cellar (memory) for every single word of a dish's description. Fetching takes far longer than reading. So the chef keeps notes on what is already written (KV cache), reads the book once for a whole table of orders (batching), lets an apprentice draft a few words that the chef checks in one go (speculative decoding), and prints a pocket edition of the book (quantisation).

Good at
  • KV cache, batching and speculative decoding leave outputs unchanged
  • 4-bit weights make 70B models fit on one or two GPUs
  • Order-of-magnitude cost cuts from software alone
Watch out for
  • The KV cache can outgrow the weights at long contexts
  • Bigger batches raise throughput but slow each user down
  • Low-bit quantisation can hurt rare skills more than benchmarks show

1Prefill, decode and the KV cache

Choose a model and a workload. The calculator sizes the KV cache; the chart compares the work per generated token with and without it.

Recall self-attention: each new token's query \(q_t\) is compared with the keys \(k_1,\dots,k_t\) of every token so far, and the output is a weighted sum of their values:

$$o_t=\sum_{s\le t}\operatorname{softmax}_s\!\Big(\frac{q_t\cdot k_s}{\sqrt{d_h}}\Big)\,v_s .$$

The keys and values of earlier tokens do not change when a new token arrives (the causal mask guarantees it). So we compute each token's \(k_s, v_s\) once, in every layer and head, and keep them: the KV cache. Generation then has two phases:

  • Prefill: the whole prompt goes through in one parallel pass, filling the cache. This is big matrix–matrix work, and fast.
  • Decode: each step feeds just the newest token, appends its \(k,v\) to the cache, and attends over the cache. Without the cache, step \(t\) would recompute all \(t\) tokens: total work grows like \(t^2\) instead of \(t\). The chart shows the gap.

The price is memory. Per token, the cache holds a key and a value vector per layer per KV head:

$$\text{KV bytes per token}=2\times n_{\text{layers}}\times n_{\text{kv heads}}\times d_{\text{head}}\times\text{bytes per number}.$$

Llama 2 7B (32 layers, 32 heads of 128) needs 0.5 MB per token in 16-bit, so a 4k-token conversation takes 2 GB, and 16 such users need 32 GB, more than twice the model's own weights. Grouped-query attention (GQA) shares each key/value head among several query heads: Llama 3 uses 8 KV heads for 32 query heads, cutting the cache by 4× with little loss in quality. Multi-query attention (MQA) goes all the way to one KV head.

Algorithm: generation with a KV cache
  1. input prompt tokens \(x_{1..m}\), model, max new tokens \(n\)
  2. prefill: run \(x_{1..m}\) in one pass; store \(K,V\) for every layer; get \(p(\cdot\mid x_{1..m})\)
  3. for \(t=m+1\) to \(m+n\) do
  4. pick \(x_t\) from \(p\) (greedy or sampling)
  5. run only \(x_t\) through the network; in each layer compute \(q_t,k_t,v_t\)
  6. append \(k_t,v_t\) to the cache; attend \(q_t\) over all cached keys O(t) work, not O(t²)
  7. if \(x_t\) is the end token then stop
  8. return \(x_{m+1..t}\)

Adapted from: Ainslie et al., GQA: Training Generalized Multi-Query Transformer Models from Multi-Head Checkpoints (2023); Shazeer, Fast Transformer Decoding: One Write-Head is All You Need (MQA, 2019). Model shapes from the Llama model cards.

2Why decoding is memory-bound: the roofline

One decode step must read every weight once, however many requests share it. Pick a GPU and a weight precision, then see how throughput and each user's speed change with batch size.

An idealised model: each step costs the larger of (bytes read ÷ bandwidth) and (FLOPs ÷ peak). KV-cache reads for 1,000-token contexts in 16-bit with 8 KV heads are included. Real systems reach 50–80% of these numbers.

A GPU has two speeds: how fast it computes (FLOP/s) and how fast it reads memory (bytes/s). Which one limits a job depends on its arithmetic intensity, the FLOPs done per byte read. An H100 can do about 989 TFLOP/s but read only 3.35 TB/s, so a job needs about \(989/3.35\approx295\) FLOPs per byte to keep the arithmetic units busy.

Now count one decode step for a model with \(N\) parameters stored in \(b\) bytes each, serving a batch of \(B\) requests. It reads all weights once (\(Nb\) bytes) and does about \(2N\) FLOPs per request (\(2NB\) in total):

$$\text{intensity}=\frac{2NB}{Nb}=\frac{2B}{b}\ \text{FLOPs per byte}.$$

With 16-bit weights (\(b=2\)) and one user, that is 1 FLOP per byte, about 300 times too little: the GPU spends almost all its time waiting for memory. Decoding is memory-bound, and a single user's speed is roughly

$$\text{tokens/s}\approx\frac{\text{memory bandwidth}}{\text{bytes of weights}+\text{bytes of KV cache read}}.$$

A 7B model in 16-bit (14 GB) on an H100 tops out near 240 tokens per second for one user. Three levers follow directly. Batch: \(B\) users share each weight read, so throughput grows almost linearly with \(B\) until compute or KV-cache reads take over. Quantise: 4-bit weights are a quarter of the bytes, so single-user speed nearly quadruples. Read fewer weights per token: speculative decoding (section 4) and mixture-of-experts models, which use only some of their weights per token.

Prefill is the opposite case: thousands of prompt tokens share each weight read, so it is compute-bound. That is why serving systems report two latencies: time to first token (prefill) and time per output token (decode).

Adapted from: Williams, Waterman and Patterson, Roofline: an insightful visual performance model (CACM 2009); Pope et al., Efficiently Scaling Transformer Inference (2022).

3Batching: static versus continuous

Requests with very different answer lengths share 8 batch slots. Static batching waits for the whole batch to finish; continuous batching refills a slot the moment its request ends.

Batching is what makes serving affordable, but requests are awkward to batch: one user wants a one-line answer, another a 2,000-token essay. With static batching, a batch starts together and ends when its longest request ends; slots whose request finished early sit idle (grey in the chart) and new requests wait in the queue.

Continuous batching (also called iteration-level scheduling, introduced by the Orca system) makes the scheduling decision at every decode step instead of once per batch: as soon as a request emits its end token, its slot is given to the next request in the queue, whose prompt is prefilled and joined to the running batch. Utilisation stays near 100%, and throughput rises most when lengths vary widely; move the spread slider to see it.

The other half of the problem is memory. Each request's KV cache grows as it generates, and nobody knows in advance how long it will get. Reserving the maximum length per request wastes most of the memory. PagedAttention, from the vLLM project, borrows an idea from operating systems: split the cache into fixed-size blocks (say 16 tokens), allocate blocks on demand, and keep a block table per request, like virtual-memory pages. Waste drops to under one block per request, so far more requests fit in a batch, and identical prompt prefixes (a shared system prompt) can share blocks.

Going deeper: chunked prefill, prefix caching and disaggregation

A long prompt's prefill can stall everyone else's decode steps. Chunked prefill splits it into pieces interleaved with decode steps. Prefix caching keeps the KV blocks of common prompt prefixes between requests, which is what provider-side prompt caching sells. Some large deployments go further and disaggregate: prefill runs on one pool of GPUs, which are compute-bound, and decode on another, which are memory-bound, each sized for its job.

Adapted from: Yu et al., Orca: A Distributed Serving System for Transformer-Based Generative Models (OSDI 2022); Kwon et al., Efficient Memory Management for Large Language Model Serving with PagedAttention (SOSP 2023).

4Speculative decoding: guess fast, check in one pass

Left: the big model's next-token distribution \(p\) and a small draft model's \(q\). Run 20,000 speculative samples and check the output matches \(p\) exactly. Right: the expected speed-up.

Decoding is memory-bound, so a forward pass that checks 5 tokens costs about the same as one that produces 1: the weights are read once either way. Speculative decoding exploits this. A small, fast draft model guesses the next \(k\) tokens one by one; the large target model scores all \(k\) positions in a single pass; the longest acceptable prefix is kept. Easy stretches of text (“the United States of ___”) are accepted wholesale.

The clever part is that the output is not merely close to the big model's: it is exactly distributed as the big model's samples. For each drafted token \(x\sim q\), accept it with probability

$$\min\Big(1,\;\frac{p(x)}{q(x)}\Big),\qquad\text{otherwise sample a replacement from }\;p'(x)=\frac{\max\big(0,\,p(x)-q(x)\big)}{\sum_{x'}\max\big(0,\,p(x')-q(x')\big)} .$$

Why is this exact? The probability of emitting token \(x\) is the chance it was drafted and accepted, \(q(x)\min(1,p(x)/q(x))=\min(q(x),p(x))\), plus the chance of a rejection times \(p'(x)\). The rejection probability is \(1-\sum_x\min(p,q)=\sum_x\max(0,p-q)\), so the second term is exactly \(\max(0,p(x)-q(x))\). Adding the two, \(\min(p,q)+\max(0,p-q)=p(x)\). The histogram in the lab checks it.

The acceptance rate per token is \(\alpha=\sum_x\min(p(x),q(x))\). If acceptances were independent with rate \(\alpha\), one target pass would produce on average

$$\mathbb E[\text{tokens per target pass}]=\frac{1-\alpha^{k+1}}{1-\alpha},\qquad\text{speed-up}\approx\frac{1-\alpha^{k+1}}{(1-\alpha)(1+kc)} ,$$

where \(c\) is the cost of a draft step relative to a target step. Good drafts (\(\alpha\approx0.7\)–\(0.8\)) give 2–3× in practice.

Algorithm: speculative sampling (one step)
  1. input prefix, target \(p\), draft \(q\), lookahead \(k\)
  2. for \(i=1..k\): draw \(\tilde x_i\sim q(\cdot\mid\text{prefix},\tilde x_{<i})\) cheap, sequential
  3. one target pass gives \(p(\cdot\mid\text{prefix},\tilde x_{<i})\) for \(i=1..k{+}1\) parallel
  4. for \(i=1..k\): with prob. \(\min(1,p(\tilde x_i)/q(\tilde x_i))\) accept \(\tilde x_i\)
  5. else sample \(x\sim\operatorname{norm}(\max(0,p-q))\), append it, stop
  6. if all \(k\) accepted: sample one bonus token from \(p(\cdot\mid\ldots,\tilde x_k)\)
  7. return between 1 and \(k+1\) new tokens
Going deeper: no draft model at all

A separate draft model has to share the tokenizer and be kept in memory. Alternatives draft from the big model itself: Medusa adds extra heads that predict tokens 2, 3, … ahead; EAGLE trains a small head on the target's hidden states; prompt lookup drafts by copying n-grams from the prompt, which works remarkably well for editing and summarising. All use the same verify step.

Adapted from: Leviathan, Kalman and Matias, Fast Inference from Transformers via Speculative Decoding (ICML 2023); Chen et al., Accelerating Large Language Model Decoding with Speculative Sampling (2023), Algorithm 2 and Theorem 1.

5Weight quantisation: RTN, GPTQ and AWQ, live

A real-sized slice of a layer: 32 outputs × 128 inputs, with 512 calibration inputs in which a few channels carry much larger activations, as in real LLMs. Each method rounds the weights to b bits; the error is measured on the layer's outputs.

Relative output error ‖XW − XŴ‖² / ‖XW‖² on the calibration data, log scale. GPTQ and AWQ use the calibration data; round-to-nearest (RTN) does not.

The compression page introduced round-to-nearest quantisation: give each group of weights one scale and round every weight to the nearest of \(2^b\) levels. At 8 bits that is nearly free; at 3–4 bits on large LLMs, plain rounding starts to hurt. The two most used fixes both change the question from “how close are the weights?” to “how close are the layer's outputs on real inputs?” For a layer \(y=Wx\) and calibration inputs \(X\), they target

$$\min_{\hat W\in\text{grid}}\;\big\|XW^\top-X\hat W^\top\big\|_F^2 .$$

GPTQ (Frantar et al., 2022) quantises the weights of each row one column at a time, and after rounding a column it updates the not-yet-quantised columns to cancel the error just made. The best correction comes from the inverse of \(H=X^\top X\), which says how inputs correlate. With \(\delta_j=(w_j-\hat w_j)/[H^{-1}]_{jj}\), the remaining weights move by \(-\delta_j\,[H^{-1}]_{j,\,j+1:}\). It comes from Optimal Brain Surgeon (1993), made fast enough for 175B-parameter models in a few GPU-hours by processing columns in a fixed order and using a Cholesky factor of \(H^{-1}\).

AWQ (Lin et al., 2023) starts from an observation: a small share of input channels have much larger activations, and the weights that multiply them matter most. Scaling those weight columns up by \(s_j\) before rounding (and the inputs down by \(s_j\), so the product is unchanged) gives them finer effective resolution. It picks \(s_j=(\text{mean}|x_j|)^{\gamma}\), with \(\gamma\) chosen by a small grid search on the output error. No weight updates, no Hessian, and robust to the calibration set.

Algorithm: GPTQ for one weight matrix
  1. input weights \(W\) (rows × columns), calibration inputs \(X\), bits \(b\), group size \(g\)
  2. \(H\leftarrow X^\top X+\lambda I\); \(U\leftarrow\) upper Cholesky factor of \(H^{-1}\) shared by all rows
  3. for column \(j=1..d\) do
  4. if \(j\) starts a group: set the group's scale from the current weights
  5. \(\hat w_{:,j}\leftarrow\operatorname{round}(w_{:,j})\); \(\delta\leftarrow(w_{:,j}-\hat w_{:,j})/U_{jj}\)
  6. \(w_{:,j+1:}\leftarrow w_{:,j+1:}-\delta\,U_{j,j+1:}\) push the error onto later columns
  7. return \(\hat W\)

GGUF is a file format rather than an algorithm: the single-file format of llama.cpp, used by Ollama and LM Studio to run models on CPUs, Macs and consumer GPUs. It stores weights in block-wise formats such as Q8_0 (blocks of 32 weights, one 16-bit scale: 8.5 bits per weight) and the “k-quants” Q2_K to Q6_K (super-blocks of 256 with quantised sub-block scales, about 2.6 to 6.6 bits per weight). Mixes such as Q4_K_M keep sensitive tensors at higher precision; an importance matrix (“imatrix”) computed on calibration text plays a role similar to AWQ's activation statistics.

6The same thing in Python

Hugging Face transformers for the KV cache and speculative (assisted) decoding, vLLM for serving, and the usual routes to a 4-bit model.

# pip install torch transformers accelerate vllm bitsandbytes
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig

tok = AutoTokenizer.from_pretrained("meta-llama/Llama-3.1-8B-Instruct")
big = AutoModelForCausalLM.from_pretrained("meta-llama/Llama-3.1-8B-Instruct",
                                           torch_dtype=torch.bfloat16, device_map="auto")
inputs = tok("Explain the KV cache in one paragraph.", return_tensors="pt").to(big.device)

# KV cache: on by default (use_cache=True); prefill happens on the first step
out = big.generate(**inputs, max_new_tokens=200, do_sample=False)

# speculative ("assisted") decoding with a small draft model that shares the tokenizer
draft = AutoModelForCausalLM.from_pretrained("meta-llama/Llama-3.2-1B-Instruct",
                                             torch_dtype=torch.bfloat16, device_map="auto")
out = big.generate(**inputs, assistant_model=draft, max_new_tokens=200, do_sample=False)
print(tok.decode(out[0], skip_special_tokens=True))

# 4-bit loading on the fly (round-to-nearest NF4, no calibration)
q4 = AutoModelForCausalLM.from_pretrained("meta-llama/Llama-3.1-8B-Instruct",
        quantization_config=BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4"))

# serving: continuous batching + PagedAttention; AWQ or GPTQ checkpoints load the same way
from vllm import LLM, SamplingParams
llm = LLM(model="meta-llama/Llama-3.1-8B-Instruct", gpu_memory_utilization=0.9)
outs = llm.generate(["Hello!", "Summarise speculative decoding."], SamplingParams(max_tokens=128))

# local inference with llama.cpp: convert, quantise to GGUF Q4_K_M, run
#   python convert_hf_to_gguf.py ./Llama-3.1-8B-Instruct --outfile model-f16.gguf
#   ./llama-quantize model-f16.gguf model-Q4_K_M.gguf Q4_K_M
#   ./llama-cli -m model-Q4_K_M.gguf -p "Hello"

GPTQ and AWQ checkpoints are usually produced with dedicated tools (for example GPTQModel or llm-compressor) and then loaded by transformers or vLLM. Commands and flags change between releases; check each project's documentation.
