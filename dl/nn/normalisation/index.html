Normalisation: keep every layer in range

Each layer's output is the next layer's input. If those inputs drift to huge values, tanh and sigmoid saturate and gradients die; if they shrink, the signal disappears. Normalisation re-centres and re-scales activations inside the network, at every step, so each layer always sees inputs of a sensible size.

What is normalisation, in plain words?

The problem

Imagine a 20-layer network halfway through training. Layer 12 has learned to expect inputs of a certain size. Then the layers below it update, and suddenly its inputs are three times bigger, or all shifted positive. Layer 12 has to re-adapt, and so does everything above it, every step. With saturating activations, big inputs also mean flat slopes and vanishing gradients. We would like each layer to receive inputs on a predictable scale no matter what the layers below are doing.

The idea

Each layer’s outputs are the next layer’s inputs. If they drift to huge values, tanh and sigmoid units saturate; if they shrink, the signal fades away. A normalisation layer rescales the numbers inside the network to a standard size (average 0, spread 1) at every step, then lets the network choose its own scale and shift with two learned numbers \(\gamma, \beta\).

The variants differ in which numbers they average over: BatchNorm uses the same feature across a mini-batch, LayerNorm uses all features of one example, RMSNorm skips the centring.

How it works

  1. Compute the mean and variance over the chosen axis.
  2. Subtract the mean and divide by the standard deviation.
  3. Multiply by \(\gamma\) and add \(\beta\) (learned).
  4. For BatchNorm, keep running averages to use at test time.

An everyday picture

Grading on a curve: every exam is rescaled so the class average and spread are the same, whatever the difficulty, so later decisions always see marks on a familiar scale.

4BatchNorm's batch problem

BatchNorm normalises one example with statistics computed from the other examples in its batch. So the same input gets a slightly different output every time it lands in a different batch. That noise acts as a mild regulariser, but:

  • Small batches give noisy estimates of \(\mu\) and \(\sigma\) (error shrinks like \(1/\sqrt{B}\)).
  • At test time there may be one example, so BatchNorm switches to running averages collected during training. Train and test behave differently, a common bug source (model.eval()).
  • Sequences have different lengths and text is generated one token at a time, so batch statistics make little sense. This is why transformers use LayerNorm or RMSNorm.

One fixed example with raw value 1.5 for a feature distributed as \(\mathcal N(0.5,\,1)\). Each dot is its BatchNorm output in one of 200 random batches of size \(B\). The dashed line is the value using the true mean and variance, which running averages approximate at test time. LayerNorm's output would not depend on the batch at all.

5The maths

BatchNorm (Ioffe & Szegedy, 2015)

$$\begin{aligned}\mu_j&=\tfrac1B\textstyle\sum_i z_{ij}\\ \sigma_j^2&=\tfrac1B\textstyle\sum_i(z_{ij}-\mu_j)^2\\ \hat z_{ij}&=\dfrac{z_{ij}-\mu_j}{\sqrt{\sigma_j^2+\epsilon}}\\ y_{ij}&=\gamma_j\hat z_{ij}+\beta_j\end{aligned}$$

Per feature \(j\), over the batch. At test time \(\mu_j,\sigma_j^2\) are exponential moving averages from training (momentum 0.1 here and in PyTorch). For images, the statistics are taken over batch, height and width for each channel.

LayerNorm (Ba, Kiros & Hinton, 2016)

$$\begin{aligned}\mu_i&=\tfrac1D\textstyle\sum_j z_{ij}\\ \sigma_i^2&=\tfrac1D\textstyle\sum_j(z_{ij}-\mu_i)^2\\ y_{ij}&=\gamma_j\dfrac{z_{ij}-\mu_i}{\sqrt{\sigma_i^2+\epsilon}}+\beta_j\end{aligned}$$

Per example \(i\), over its \(D\) features. Identical in training and testing, and independent of the batch.

RMSNorm (Zhang & Sennrich, 2019)

$$y_{ij}=\gamma_j\dfrac{z_{ij}}{\sqrt{\tfrac1D\sum_k z_{ik}^2+\epsilon}}$$

Drops the mean subtraction and \(\beta\). About as good as LayerNorm and cheaper, so LLaMA, Mistral and most recent LLMs use it.

The same recipe, two directions

All three methods do the same three things: measure a mean and a spread, standardise, then let the network rescale. The only difference is which numbers are pooled together: down a column of the batch (BatchNorm) or along a row, one example at a time (LayerNorm).

Algorithm: BatchNorm and LayerNorm forward pass
  1. input activations \(Z\) (\(B\) examples × \(D\) features), learnable \(\gamma,\beta\in\mathbb R^D\), \(\epsilon\)
  2. BatchNorm: for each feature (column) \(j\) do
  3. \(\mu_j\leftarrow\) mean of column \(j\); \(\sigma_j^2\leftarrow\) its variance pooled over the batch
  4. \(\hat Z_{:,j}\leftarrow(Z_{:,j}-\mu_j)/\sqrt{\sigma_j^2+\epsilon}\)
  5. update running averages of \(\mu_j,\sigma_j^2\) used at test time instead
  6. LayerNorm: for each example (row) \(i\) do
  7. \(\mu_i\leftarrow\) mean of row \(i\); \(\sigma_i^2\leftarrow\) its variance pooled over features
  8. \(\hat Z_{i,:}\leftarrow(Z_{i,:}-\mu_i)/\sqrt{\sigma_i^2+\epsilon}\)
  9. return \(Y=\gamma\odot\hat Z+\beta\) same final step for both
Going deeper: why BatchNorm behaves differently at test time

During training, each example's output depends on the other examples in its batch, through \(\mu_j\) and \(\sigma_j\). That is a mild source of noise (a regulariser) but a problem for prediction: the answer for one test image must not depend on which other images happen to be processed with it, and a batch of size 1 has no variance at all. So at test time BatchNorm switches to fixed population estimates, the running averages \(\bar\mu\leftarrow(1-m)\bar\mu+m\mu_{\text{batch}}\) collected in training. The train/test mismatch causes real bugs: forgetting model.eval(), tiny batches, or a distribution shift between training and deployment.

LayerNorm never looks across examples, so it is identical in training and testing and works with any batch size, including the one-token-at-a-time generation of a language model. That, plus variable sequence lengths, is why transformers use LayerNorm or RMSNorm.

Why \(\gamma\) and \(\beta\)?

Forcing every layer to mean 0, variance 1 would limit what the network can represent (a sigmoid would only ever see its near-linear middle). The learnable \(\gamma,\beta\) let the layer undo the normalisation if that is best, with \(\gamma=\sigma,\beta=\mu\). What changes is the parameterisation: scale and shift are now two direct knobs instead of an emergent property of all the weights below.

Backward pass (BatchNorm)

$$\frac{\partial\mathcal L}{\partial z_{ij}}=\frac{\gamma_j}{\sigma_j}\Big(g_{ij}-\overline{g}_{j}-\hat z_{ij}\,\overline{g\hat z}_{j}\Big)$$

with \(g=\partial\mathcal L/\partial y\) and bars meaning averages over the batch. The gradient is projected so it cannot change the batch mean or variance: this is what the engine on this site implements (a gradient check agrees to about \(10^{-4}\)). LayerNorm has the same formula with averages over features.

Why does it work? The original paper argued it reduces "internal covariate shift" (layer inputs changing distribution as earlier layers learn). Santurkar et al. (2018) showed the bigger effect is a smoother loss landscape: gradients change less from step to step, so larger learning rates are safe. Normalised layers are also scale invariant (multiplying the weights below by \(c\) changes nothing), which keeps them from blowing up.

Placement matters too: in a transformer, pre-LN (normalise the input of each sub-block, keep the residual path clean) trains stably without warm-up; post-LN (normalise after adding) was the 2017 original and needs care. In CNNs the classic order is convolution → BatchNorm → ReLU.

7The same thing in Python (PyTorch)

bn  = nn.BatchNorm1d(64)      # over the batch, per feature; uses running stats in eval()
ln  = nn.LayerNorm(64)        # over the last dimension of each example
rms = nn.RMSNorm(64)          # PyTorch 2.4+; LLaMA-style

model = nn.Sequential(nn.Linear(2, 64), nn.BatchNorm1d(64), nn.Tanh(),
                      nn.Linear(64, 64), nn.BatchNorm1d(64), nn.Tanh(), nn.Linear(64, 1))
model.train()   # batch statistics, updates running_mean / running_var
model.eval()    # running averages: ALWAYS switch before evaluating
