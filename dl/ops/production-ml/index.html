Production ML: a model is not a product

A trained model in a notebook is perhaps 5% of a working ML system. The rest is getting data in reliably, computing features the same way in training and in production, answering requests fast enough, noticing when the world changes, and replacing the model without breaking anything. This page walks through each part with small simulations you can push until they fail.

What is MLOps, in plain words?

The problem

Models that score well offline often fail in production, quietly. The data pipeline changes a unit, a feature is computed slightly differently at serving time, customers start behaving differently, or a new model version is worse on a slice nobody tested. Unlike a crash, a wrong prediction raises no error.

The idea

MLOps applies software-engineering discipline (automation, testing, versioning, monitoring) to the whole life of a model: data, features, training, deployment and the feedback loop that triggers retraining. Every step is reproducible, every change is tested, and every model in production is watched.

How it works

  1. Version data, code and configuration; train in a pipeline, not by hand.
  2. Compute features once, in a feature store, for both training and serving.
  3. Register each model with its metrics and lineage; roll it out gradually (shadow, then canary).
  4. Monitor inputs, outputs and outcomes for drift; retrain or roll back when they move.

An everyday picture

A restaurant. The recipe (the model) matters, but so do reliable suppliers (data pipelines), a prep station that cuts ingredients the same way every day (features), a kitchen that serves the lunch rush on time (serving), tasting before a new dish goes on the menu (canary), and noticing when customers' tastes change (drift).

Buys you
  • Models that keep working after launch
  • Fast, safe iteration: many small releases instead of risky big ones
  • Audit trails: which data and code produced this prediction?
Costs you
  • Infrastructure and process before the first model ships
  • Monitoring needs ground-truth labels, which often arrive late
  • Easy to over-engineer for a model that runs once a month

1The ML system lifecycle

Click a stage to see what happens there, what typically goes wrong, and common tools. The dashed arrow is the feedback loop.

Sculley et al. (2015) drew the now-famous picture of a production ML system as a small "ML code" box surrounded by much larger boxes: data collection, verification, feature extraction, configuration, serving infrastructure, monitoring. They called the gap hidden technical debt: ML systems have all the maintenance problems of ordinary code, plus new ones, because their behaviour is set by data rather than written down.

Three kinds of debt to watch:

  • Entanglement ("changing anything changes everything"): add one feature and the weights of all the others shift.
  • Hidden feedback loops: a recommender changes what users click, which becomes next month's training data.
  • Pipeline jungles and glue code: scripts that turn raw data into features in five slightly different ways.

The lifecycle on the left is the antidote: a single, automated path from raw data to a monitored prediction, with a loop back. Each later section zooms into one arrow.

Who does what: data engineers own ingestion and the feature pipelines, ML engineers own training pipelines, serving and monitoring, and data scientists own the modelling and evaluation choices. In small teams these are the same people, which is why automation matters even more.

2Serving: batch, real-time and dynamic batching

A simulated GPU server. Requests arrive at random; the server waits up to "max wait" to collect up to "max batch" requests, then runs them together. Curves: median and 99th-percentile latency for every max batch size.

There are three ways to get predictions to users:

When predictions are madeGood for
BatchOn a schedule, for everyone, stored in a tableNightly churn scores, weekly pricing, email campaigns
OnlineOn request, behind an API, in millisecondsFraud checks at payment, search ranking, chatbots
StreamingAs events arrive, with features from a streamReal-time anomaly detection, live recommendations

Batch is cheaper and simpler but the prediction can be up to a day old and is computed even for users who never come back. Online is fresh but every millisecond counts, and users notice the slowest requests, not the average. That is why services are judged by tail latency, the 99th percentile (p99).

Accelerators are much more efficient on a batch: running 32 inputs together may cost only a little more than running one. Dynamic batching trades a little waiting for that efficiency. The simulator charges 8 ms per batch plus 0.6 ms per request. Each server has a capacity limit: with batch size \(b\), at most \(b/(8+0.6b)\) requests per millisecond. Push the traffic to 600 per second with max batch 1: the queue grows without bound and p99 explodes. Raise the max batch and the same hardware copes. Then raise the max wait and watch the median latency pay for it at low traffic.

Going deeper: why queues blow up near capacity

Queueing theory gives the shape. For the simplest queue (random arrivals at rate \(\lambda\), random service times with rate \(\mu\)), the mean time in the system is \(1/(\mu-\lambda)\): with utilisation \(\rho=\lambda/\mu\), latency scales like \(1/(1-\rho)\). At 50% utilisation you wait twice the service time; at 90%, ten times; at 99%, a hundred times. Servers are therefore run well below capacity, and autoscaling adds replicas before \(\rho\) gets close to 1. The tail is worse than the mean, which is why p99 targets drive capacity planning.

3Feature stores and the point-in-time join

Six customers. Dots: daily snapshots of "logins in the last 7 days". Vertical bar: the day we must predict churn. Ring: the snapshot each join attaches to that training example.

Join

A model can only be as good in production as its features are identical in production. Training–serving skew is any difference between the features the model trained on and the ones it receives live: a different code path (SQL offline, Java online), a different time window, a missing-value default, or, most sneakily, information from the future.

A feature store attacks skew by defining each feature once and serving it two ways: an offline store keeps the full history of every feature value with timestamps, for building training sets; an online store keeps only the latest value of each feature, in a fast key-value database, for serving.

Building a training set then needs a point-in-time join: for each label event at time \(t\), attach the most recent feature value with timestamp \(\le t\), exactly what the online store would have returned at that moment. Switch to the naive join, which takes the latest value in the table. Customers who churned stopped logging in after the decision day, so their latest snapshot says 0 logins. The model learns "0 logins means churn", scores brilliantly offline, and is useless live, where nobody's future is visible yet. This is leakage through time.

Popular feature stores include Feast (open source), Tecton, and the ones built into Databricks, SageMaker and Vertex AI.

4Detecting data drift and concept drift

90 days of a deployed credit model. Upper chart: PSI of the main input feature against the training data, per day (alarm above 0.2). Lower chart: the model's accuracy, known only after the label delay.

What changes on day 40

A model learns \(p(y\mid x)\) from data drawn from \(p(x)\). Either can move after deployment (see distribution shift):

  • Data drift (covariate shift): \(p(x)\) changes, \(p(y\mid x)\) does not. New customer segments, a new app version, a sensor recalibrated. You can see it immediately, from inputs alone.
  • Concept drift: \(p(y\mid x)\) changes. An interest-rate shock changes who defaults at the same income; fraudsters adapt. Inputs may look identical, so only outcomes reveal it, and outcomes arrive late.

Two standard tests for one feature, comparing a reference window (training data) to a live window:

$$\text{PSI}=\sum_{b=1}^{B}(p_b-q_b)\ln\frac{p_b}{q_b},\qquad D_{\text{KS}}=\sup_x\big|F_{\text{live}}(x)-F_{\text{ref}}(x)\big|.$$

The population stability index bins the feature (\(q_b\): reference share, \(p_b\): live share); a common rule of thumb reads under 0.1 as stable, 0.1 to 0.2 as moderate and over 0.2 as a significant shift. The Kolmogorov–Smirnov statistic is the largest gap between the two cumulative distributions, with a p-value. Beware: with large samples every tiny shift is "significant", so alert on effect sizes, not p-values.

Compare the two scenarios. Covariate shift trips the PSI alarm on day 40; accuracy may or may not suffer. Concept drift leaves PSI flat, and you learn about it only when labels arrive, a label delay later. Hence the usual stack: monitor inputs and prediction distributions (fast, label-free), monitor performance as labels land (slow, definitive), and retrain on a schedule or when either alarm fires.

Algorithm: daily drift monitor for one feature
  1. input reference sample \(R\) (training data), bins \(b_1..b_B\) from quantiles of \(R\), threshold τ
  2. \(q_b\leftarrow\) share of \(R\) in each bin add a tiny ε to avoid log 0
  3. each day
  4. collect the live window \(L\) of inputs
  5. \(p_b\leftarrow\) share of \(L\) in each bin
  6. \(\text{PSI}\leftarrow\sum_b(p_b-q_b)\ln(p_b/q_b)\)
  7. if PSI \(>\) τ: raise an alert, investigate, consider retraining

5Shadow, canary and automatic rollback

A canary sends a share of live traffic to the new model for 48 hours. Lines: running error rates with 95% bands. The release is rolled back as soon as the canary is significantly worse.

Offline metrics are estimates; production is the test. Release strategies limit the damage a bad model can do:

  • Shadow deployment: the new model receives a copy of live traffic and its predictions are logged, never used. Zero user risk; it catches crashes, latency problems and skew, and lets you compare predictions. It cannot measure effects on behaviour (clicks, purchases), because users never see its output.
  • Canary: a small share of real traffic goes to the new model; if guard-rail metrics hold, the share is stepped up (1% → 5% → 25% → 100%).
  • A/B test: a fixed division of traffic, run long enough to measure the business metric with a pre-planned sample size and significance test.
  • Blue–green: two full environments, switch the router, keep the old one warm for an instant rollback.

The lab's baseline makes 5% errors. Every hour it compares the canary's error rate to the baseline's with a one-sided two-proportion z-test, rolling back if \(z>3\) (a strict bar, because we look 48 times). With a 5% share, a model at 6.2% error is often caught within a day or two; at 1% share the evidence arrives too slowly. A larger canary detects problems sooner but exposes more users: that is the trade-off you are choosing.

Algorithm: canary release with automatic rollback
  1. input baseline model \(M_0\), candidate \(M_1\), traffic share \(s\), threshold \(z^*\)
  2. for each hour \(h=1,\dots,H\)
  3. route each request to \(M_1\) with probability \(s\), else \(M_0\)
  4. update error counts \(e_0,n_0\) and \(e_1,n_1\)
  5. \(z\leftarrow(\hat p_1-\hat p_0)/\sqrt{\hat p(1-\hat p)(1/n_0+1/n_1)}\) pooled \(\hat p\)
  6. if \(z>z^*\): roll back to \(M_0\) and stop
  7. promote \(M_1\) (raise \(s\) in stages)

6CI/CD for ML: test the data, the model and the code

Classic software has continuous integration (every change is built and tested) and continuous delivery (every passing build can be released). ML adds continuous training: the pipeline itself is the product, and it retrains on new data automatically. Google's MLOps maturity levels describe the path: level 0, manual notebooks; level 1, an automated training pipeline with continuous training; level 2, CI/CD that tests and deploys the pipeline itself.

A model registry (MLflow, SageMaker, Vertex AI) stores every model version with its lineage (data snapshot, code commit, hyperparameters, metrics) and its stage (staging, production, archived). A model card records what it is for, how it was evaluated, and where it should not be used.

Reproducibility needs four things pinned: the data version (DVC, lakeFS, table snapshots), the code commit, the environment (container image), and random seeds.

TestExamples
Data validationSchema and types; ranges; null rates; category sets; row counts; freshness (Great Expectations, TFDV, pandera)
Feature testsSame value offline and online for sampled keys; no future timestamps
Model quality gateBeats the production model on a fixed holdout by a set amount; no slice worse by more than \(x\)%; calibration holds
Behavioural testsInvariance (changing a name does not change a sentiment score); directional expectations; minimum functionality (CheckList)

The ML Test Score (Breck et al., 2017) turns 28 such checks into a readiness rubric.

import numpy as np
from scipy.stats import ks_2samp

# population stability index with quantile bins from the reference data
def psi(ref, live, bins=10, eps=1e-6):
    edges = np.quantile(ref, np.linspace(0, 1, bins + 1)); edges[0], edges[-1] = -np.inf, np.inf
    q = np.histogram(ref, edges)[0] / len(ref) + eps
    p = np.histogram(live, edges)[0] / len(live) + eps
    return float(np.sum((p - q) * np.log(p / q)))
