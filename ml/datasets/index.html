Datasets: where honest scores come from

Models learn whatever the data teach them, and a score is only as honest as the data it was measured on. This page covers how to split data, the ways a test score can lie (reuse, leakage, imbalance, shift), how much data you need, and the datasets that shaped the field.

Why datasets need care, in plain words

The idea

We want to know how a model will do on data it has never seen, because that is what happens once it is used. So we hide some data from it. The training set is for learning, the validation set is for choosing between models and settings, and the test set is opened once, at the end, to report the final score.

How it works

  1. Collect data that look like what the model will meet in use.
  2. Split it before looking closely, keeping related examples together and class proportions stable.
  3. Train on one part, tune on the second, report on the third.
  4. Check that nothing from the test part leaked into the other two.

An everyday picture

A teacher who hands out the exam questions as homework will see excellent exam results that mean nothing. Every trap on this page is a version of that: the model, or the person tuning it, has already seen the exam.

Good habits
  • Split by user, patient or time, not by row, when rows are related
  • Stratify when a class is rare
  • Keep a final test set you never tune on
Watch out for
  • Duplicates across splits
  • Features that are only known after the outcome
  • Benchmarks your model may have read during training

How to score a model once the data are right is on the metrics page.

1Why a separate test set: the winner's curse

You try many models that are, in truth, all equally good (70% accurate). You pick the one with the best validation score, then check it on a fresh test set. Purple: the winner's validation score. Orange: the same model on the test set. Repeated 300 times.

Each validation score is the true accuracy plus noise, because the validation set is a finite sample. Pick the maximum of many noisy scores and you pick the luckiest noise. The more models you try and the smaller the validation set, the more optimistic the winner's score. The fresh test set has no such selection, so it tells the truth.

This is why there are three sets, not two. It is also why “we tried 500 hyperparameter settings and report the best validation score” is not a result, and why public leaderboards slowly overfit: thousands of teams together make thousands of choices on the same test set.

Algorithm: stratified train/validation/test split
  1. input examples with labels, fractions \(f_{\text{train}}, f_{\text{val}}, f_{\text{test}}\), random seed
  2. group examples that must stay together (same user, patient or document) avoid leakage between near-twins
  3. for each class \(c\) do
  4. shuffle the groups of class \(c\) with the seed
  5. cut them at \(f_{\text{train}}\) and \(f_{\text{train}}+f_{\text{val}}\) each split gets the same class mix
  6. combine the pieces of every class into train, validation and test
  7. return the three sets; lock the test set away until the very end
Going deeper: cross-validation, nested CV and time series

With little data, holding out 20% twice is expensive. \(K\)-fold cross-validation rotates the validation role through \(K\) parts and averages, so every example is used for both training and validation. If you also tune hyperparameters, wrap it in an outer loop (nested cross-validation) so the reported score never saw the tuning.

For time series, random splits let the model peek at the future. Always train on the past and test on a later period, ideally with a gap; scikit-learn's TimeSeriesSplit does a rolling version.

2Rare classes: why stratify

A dataset of \(n\) examples with a rare positive class is split 80/20 at random 2,000 times. Bars: how many positives land in the test set. The green line is what a stratified split gives every time.

With 1,000 examples and 2% positives there are only 20 positives in total, and a random 20% test set should get 4 of them. It often gets 1, 2, 6 or 7, and occasionally none, in which case recall cannot even be computed. The test score then depends on the luck of the split as much as on the model. A stratified split fixes the count in each part.

Imbalance also affects training. Common remedies: weight the rare class more in the loss, resample (oversample positives, undersample negatives, or generate synthetic examples with SMOTE), and choose the threshold and metric for the real costs (precision–recall rather than accuracy).

3Leakage and contamination: when the model has seen the exam

A model that has partly memorised its training data is tested on a set where some examples also appear (exactly or nearly) in training. Purple: the score you report. Green: the score it will get on genuinely new data.

Leakage is anything that lets test information into training. Common forms:

  • Duplicates and near-duplicates across splits: the same photo resized, the same sentence with different punctuation, the same patient scanned twice.
  • Target leakage: a feature only known after the outcome, such as “treatment given” when predicting a diagnosis, or “claim paid date” when predicting a claim.
  • Preprocessing on all the data: fitting a scaler, imputation or feature selection before splitting lets test statistics shape training.
  • Time travel: random splits of time-ordered data.
  • Benchmark contamination: large language models are trained on much of the web, which contains many public test sets. A model can then recall answers instead of solving the questions.
Algorithm: checking for train–test overlap
  1. input training documents, test documents, n-gram length \(n\) (e.g. 13 words)
  2. for each training document do add the hash of every \(n\)-gram to a set \(H\) normalise case and spacing first
  3. for each test document \(d\) do
  4. overlap\((d)\leftarrow\) share of \(d\)'s \(n\)-grams whose hash is in \(H\)
  5. if overlap\((d)\) is above a threshold then flag \(d\) as contaminated
  6. return scores on the clean and flagged subsets separately a big gap means leakage

4Distribution shift: the world moves after you train

The true rule is curved (shaded regions). The model learned a straight-line boundary from training data near the centre (grey dots). Shift where the new data come from (orange dots) and watch accuracy.

Test sets are usually drawn from the same pool as training data, so they cannot warn you when the world changes. Three kinds of shift:

  • Covariate shift: the inputs change, the rule does not. A model trained on daytime photos meets night photos; the demo above shows this. A model can be perfect where it was trained and wrong just outside.
  • Label (prior) shift: the class mix changes, such as fraud rates rising in a crisis. Precision changes even if the model does not.
  • Concept drift: the rule itself changes, such as what counts as spam, or how customers react to a new price.

Defences: collect test data from the deployment setting, monitor input statistics and scores over time, keep a recent hold-out set, and retrain on a schedule.

5How much data do you need? Learning curves and scaling laws

Test error against training-set size, on log scales. Each curve is a model of a different size. Small models plateau early; larger ones keep improving if they get more data.

A learning curve answers the most practical question in ML: will more data help? Empirically, test error falls roughly as a power law, \(\text{err}(n)\approx E+A\,n^{-\alpha}\), where \(E\) is the irreducible error (label noise) and \(\alpha\) is often between 0.1 and 0.5. On log scales the curve is close to a straight line until it flattens towards its floor.

If the training error is also high, the model is too small (high bias) and more data will not help much; a bigger model will. If training error is low but test error high, the model is overfitting (high variance), and more data will help.

Language models made this quantitative. Scaling laws (Kaplan et al., 2020; Hoffmann et al., 2022, “Chinchilla”) show loss falling as a power law in parameters, data and compute together. For a fixed compute budget the Chinchilla result is to grow model and data together, at roughly 20 training tokens per parameter. Current models are trained on far more tokens than that, because a smaller model trained longer is cheaper to run.

6The datasets that shaped the field

Each dot is a famous dataset, by year and size (log scale). Sizes count examples, image–text pairs or words/tokens as noted, so compare orders of magnitude only. Tap a dot for details.

Progress has repeatedly come from a new dataset rather than a new algorithm: MNIST made neural networks measurable, ImageNet made deep CNNs possible, SQuAD and GLUE drove pre-trained language models, and web-scale corpora made LLMs. Each benchmark then saturates: GLUE was matched by models within about a year, SuperGLUE within two, and recent LLM benchmarks within months, which is why evaluation keeps moving to harder and fresher tests.

7Documenting and handling data responsibly

Datasheets and data cards

For every dataset, write down: who collected it, when, and why; what population it covers and who is missing; how labels were made and how much annotators agreed; known errors and biases; the licence; and what it should not be used for. “Datasheets for datasets” (Gebru et al., 2018) and Hugging Face dataset cards are standard templates.

Label quality

Even famous test sets contain label errors (estimates for ImageNet's validation set are a few percent). When models are near the top, errors in the test labels decide the ranking. Tools such as confident learning find likely mislabelled examples for review.

Privacy, consent and licences

Personal data needs a lawful basis and minimisation (GDPR in Europe, the DPDP Act in India). Web-scraped data raises copyright and consent questions that are still being decided in courts. Keep a record of sources and licences, and remove personal identifiers you do not need.

Bias

A model trained on a skewed sample reproduces the skew: face datasets that under-represent darker skin, credit data that reflect past lending decisions. Report metrics per group, not only overall.
