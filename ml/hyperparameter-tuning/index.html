Hyperparameter optimisation: tuning without fooling yourself

Every model has knobs it cannot learn from the data: the depth of a tree, the strength of a penalty, the learning rate of a network. Choosing them is itself a search, with a budget and a risk of overfitting the validation set. This page compares the ways to search, from a plain grid to Bayesian optimisation and Optuna, and shows how to report a score you can trust afterwards.

What is hyperparameter optimisation, in plain words?

The problem

Parameters (weights, coefficients, split thresholds) are learned by training. Hyperparameters are fixed before training starts: how deep, how fast, how much penalty, how many neighbours. Bad choices can turn a good algorithm into a bad model, and the best values depend on the data, so there is no universal default.

The idea

Treat “train the model with settings \(\lambda\) and measure its validation score” as a black-box function \(f(\lambda)\), expensive to evaluate and noisy, and search for its best value within a budget:

  1. Define a search space: which settings, which ranges, on which scale.
  2. Pick a strategy: grid, random, or a model-based one that learns where to look next (Bayesian optimisation).
  3. Score each candidate with cross-validation, never the test set.
  4. Retrain the winner on all training data; report its score on untouched data.

An everyday picture

Perfecting a recipe: oven temperature, baking time, amount of sugar. Each trial costs a whole cake. You would not bake every combination on a fine grid; you would try a few spread-out guesses, notice what worked, and try near the best ones, while remembering that one tasting can be lucky. That is Bayesian optimisation and cross-validation, in a kitchen.

Good habits
  • Search learning rates and penalties on a log scale
  • Prefer random or Bayesian search to a big grid
  • Stop bad trials early
  • Keep a test set the search never sees
Watch out for
  • The best validation score is optimistic
  • Tuning on the test set
  • Leakage when preprocessing is outside the CV loop
  • Spending the budget on settings that do not matter

1One knob: the validation curve

A degree-12 polynomial with a ridge penalty fitted to 30 noisy points. Top: the fit at the chosen λ. Bottom: training error and 5-fold cross-validation error across λ (log scale); the dot is your λ, the ring the best.

Start with one hyperparameter. Here it is the penalty \(\lambda\) of ridge regression on polynomial features: the weights minimise \(\sum_i(y_i-w^\top\phi(x_i))^2+\lambda\lVert w\rVert^2\), so \(w\) is a parameter and \(\lambda\) a hyperparameter.

A validation curve plots the training and validation error against the hyperparameter. With tiny \(\lambda\) the curve wiggles through every point: low training error, high validation error, overfitting. With huge \(\lambda\) it flattens towards a constant: both errors high, underfitting. The best \(\lambda\) sits at the bottom of the U, which is the bias–variance trade-off drawn directly.

Two lessons carry over to everything below. First, \(\lambda\) matters on a log scale: going from 0.001 to 0.01 changes as much as from 1 to 10, so search \(\log\lambda\), not \(\lambda\). Second, the curve is noisy: the minimum of the cross-validation curve is an estimate with an error bar, and many nearby values are equally good. A common rule picks the simplest model within one standard error of the best.

2Grid search versus random search

Validation accuracy (shading, brighter = better) over two hyperparameters; only the horizontal one really matters. Dots: the trials each method spends the same budget on. The strips under and beside the map show which values of each setting were actually tried.

Grid search tries every combination of a few values per setting. With 9 trials on a 3×3 grid, the important setting is tried at only 3 values, because each one is repeated for 3 values of the unimportant setting. Random search draws each trial independently, so 9 trials try the important setting at 9 different values.

Bergstra and Bengio (2012) showed this matters in practice because of low effective dimensionality: in most models only a few hyperparameters strongly affect the score, and which ones differs between datasets. A grid wastes most of its budget varying the ones that do not matter. Random search also has useful properties: any budget, easy to run in parallel, easy to stop or extend, and adding a useless setting costs nothing.

The stats below repeat both searches 300 times: on average, how close does the best trial get to the true best score? Random search is closer for every budget, and the gap grows with the number of unimportant settings.

Algorithm: grid search and random search with cross-validation
  1. input model, search space, budget \(B\), folds \(K\)
  2. grid: candidates \(\leftarrow\) every combination of a few listed values size grows exponentially
  3. random: candidates \(\leftarrow\) \(B\) independent draws from the space log-uniform for scales
  4. for each candidate \(\lambda\) do
  5. score\((\lambda)\leftarrow\) mean \(K\)-fold validation score preprocessing inside each fold
  6. \(\lambda^\ast\leftarrow\arg\max\) score; refit on all training data with \(\lambda^\ast\)
  7. return the refitted model its CV score is optimistic: see section 6

3Bayesian optimisation: learn where to look next

The hidden curve (dashed) is validation loss against log learning rate; each evaluation costs a full training run. Purple: the Gaussian-process guess with a ±2σ band. Below: the acquisition function; its peak is where the next run goes.

Random search ignores what earlier trials found. Bayesian optimisation keeps a cheap surrogate model of the expensive function, updates it after every trial, and uses it to choose the next trial. The classic surrogate is a Gaussian process (GP): a prior over smooth functions defined by a kernel, here \(k(x,x')=\sigma_f^2\exp\!\big(-\tfrac{(x-x')^2}{2\ell^2}\big)\). After observing \(y\) at points \(X\), its prediction at \(x\) is a Gaussian with

$$\mu(x)=k_x^\top(K+\sigma_n^2I)^{-1}y,\qquad \sigma^2(x)=k(x,x)-k_x^\top(K+\sigma_n^2I)^{-1}k_x .$$

The mean is the best guess; the variance is small near tried points and large in unexplored gaps. An acquisition function turns both into a single number that balances exploitation (try where \(\mu\) is low) and exploration (try where \(\sigma\) is large). With best loss so far \(y^\ast\) and \(z=(y^\ast-\mu(x))/\sigma(x)\):

$$\text{EI}(x)=\big(y^\ast-\mu(x)\big)\,\Phi(z)+\sigma(x)\,\varphi(z),\qquad \text{LCB}(x)=\mu(x)-\kappa\,\sigma(x).$$

Expected improvement is the average amount by which \(x\) would beat the current best, counting only improvements. Press the button a few times: early points explore, then trials concentrate around the minimum, usually finding it in far fewer evaluations than a grid. Notice the second, narrower valley: a short length-scale \(\ell\) lets the GP believe in such features; a long one smooths them away.

Algorithm: Bayesian optimisation
  1. input black-box \(f\), search space, budget \(B\), surrogate (GP), acquisition \(a\)
  2. evaluate \(f\) at a few random points initial design
  3. while budget remains do
  4. fit the surrogate to all \((x,f(x))\) so far: \(\mu(x),\sigma(x)\)
  5. \(x_{\text{next}}\leftarrow\arg\max_x a(x)\) cheap: no training involved
  6. evaluate \(f(x_{\text{next}})\) expensive: one training run
  7. return the best \(x\) found
Going deeper: limits of the GP approach

A GP costs \(O(n^3)\) in the number of trials, struggles beyond about 20 dimensions, and handles categorical or conditional settings (“the number of layers only matters if the model is a network”) awkwardly. That is why practical tools use other surrogates: random forests (SMAC), tree-structured Parzen estimators (Hyperopt, Optuna, next section), or GPs with special kernels (BoTorch). Snoek, Larochelle and Adams (2012) made GP-based tuning of neural networks popular.

4TPE, the sampler inside Optuna

The same hidden curve. Trials so far are split at the γ quantile into good (green) and bad (red). Their smoothed densities l(x) and g(x) are drawn below; the next trial goes where the ratio l/g is largest (purple).

The tree-structured Parzen estimator (Bergstra et al., 2011) flips the question. Instead of modelling the score given the settings, it models the settings given the score. Split the trials into the best fraction \(\gamma\) (say 25%) and the rest, and fit a kernel density to each group:

$$l(x)=p(x\mid y\text{ in the best }\gamma),\qquad g(x)=p(x\mid y\text{ in the rest}).$$

Bergstra et al. showed that maximising expected improvement is then the same as maximising the ratio \(l(x)/g(x)\): go where good trials were common and bad ones rare. In practice TPE draws many candidates from \(l\) and keeps the one with the highest ratio.

Densities are easy to fit for any kind of setting (log-scaled numbers, integers, categories) and the search space can be a tree: a setting only exists if its parent choice was made. That flexibility is why Optuna (Akiba et al., 2019) uses TPE as its default sampler. Optuna’s “define-by-run” interface lets you write the search space as ordinary Python inside the objective, shown in section 8.

Algorithm: tree-structured Parzen estimator
  1. input objective \(f\), search space, \(\gamma\), number of candidates \(N\)
  2. run a few random trials first startup trials
  3. repeat
  4. sort the trials by score; the best \(\gamma\) share is “good”, the rest “bad”
  5. fit densities \(l(x)\) to good trials and \(g(x)\) to bad ones one Gaussian per trial
  6. draw \(N\) candidates from \(l\); keep the one with the largest \(l(x)/g(x)\)
  7. evaluate it and add it to the trials
  8. until the budget is spent; return the best trial

5Pruning: stop the losers early with successive halving

27 configurations of a network, each line its validation loss as training goes on. At each rung (dashed) the worse half is stopped (grey) and the survivors get twice the budget. The best configuration is marked; compare the compute used with training all 27 to the end.

For models trained in steps (networks, boosting), a bad configuration usually looks bad early. Successive halving (Jamieson and Talwalkar, 2016) exploits this: start many configurations with a small budget, keep the best \(1/\eta\) at each rung, multiply their budget by \(\eta\), repeat. Most of the compute goes to the promising few.

The risk is a slow starter: a configuration with a small learning rate may look worse early and win in the end. Hyperband (Li et al., 2018) hedges by running several brackets that start with different numbers of configurations and budgets. Optuna exposes these as pruners: inside the training loop you report the intermediate score with trial.report(), and trial.should_prune() tells you to stop.

Algorithm: successive halving
  1. input \(n\) configurations, minimum budget \(r\), reduction factor \(\eta\)
  2. for rung \(k=0,1,2,\dots\) do
  3. train every surviving configuration up to budget \(r\,\eta^k\) epochs, trees or samples
  4. score each on validation data
  5. keep the best \(\lceil n_k/\eta\rceil\); stop the rest
  6. until one configuration is left (or the maximum budget is reached)
  7. return the survivor

6Nested cross-validation: an honest score after tuning

Labels here are pure coin flips, so no model can truly beat 50% accuracy. We tune a k-nearest-neighbour classifier over many settings. Purple: the best cross-validated score from the search, as often reported. Green: the nested score. Averaged over repeated datasets.

After a search, the winning configuration’s cross-validation score is the maximum of many noisy estimates. As on the datasets page, the maximum of noisy numbers is optimistic: the winner was partly chosen for its luck. The more configurations you try and the smaller the data, the bigger the bias. With pure-noise labels the bias is all there is, which makes it easy to see.

Nested cross-validation puts the entire tuning procedure inside an outer loop. Each outer fold holds out data that the search never touches; the search runs on the rest with its own inner folds; the chosen model is then scored once on the outer fold. The average outer score estimates how well the procedure “tune, then train” will do on new data, which is exactly the number you want to report.

The diagram (lower chart) shows the structure: outer folds in orange, inner folds nested inside each outer training part. It costs \(K_{\text{outer}}\times K_{\text{inner}}\times\) (number of configurations) fits, so with expensive models people use a single held-out test set instead, which gives the same protection more cheaply.

Algorithm: nested cross-validation
  1. input data, search space, outer folds \(K_o\), inner folds \(K_i\)
  2. for each outer fold \(k=1..K_o\) do
  3. outer test \(\leftarrow\) fold \(k\); outer train \(\leftarrow\) the rest
  4. run the whole search on outer train, scoring each candidate by \(K_i\)-fold CV
  5. refit the winner on outer train; score it once on outer test
  6. return the mean outer score estimates “tune then train” on new data

7Hyperparameter tuning in practice

What usually matters most

A sensible workflow

  1. Get a baseline with library defaults; they are often good.
  2. Put preprocessing in a pipeline so it is refitted inside every fold.
  3. Run random search or Optuna (TPE) for a modest budget, with early stopping or pruning for iterative models.
  4. Look at the results: which settings mattered, is the best value at the edge of the range (then widen it)?
  5. Report the score on a held-out test set, or with nested CV.

8The same thing in Python

from scipy.stats import loguniform
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.svm import SVC
from sklearn.model_selection import GridSearchCV, RandomizedSearchCV, HalvingRandomSearchCV, cross_val_score, KFold
from sklearn.experimental import enable_halving_search_cv        # noqa: needed before HalvingRandomSearchCV

pipe  = make_pipeline(StandardScaler(), SVC())                      # scaler refitted inside every fold
grid  = GridSearchCV(pipe, {"svc__C": [0.1, 1, 10], "svc__gamma": [0.01, 0.1, 1]}, cv=5)
rand  = RandomizedSearchCV(pipe, {"svc__C": loguniform(1e-2, 1e3), "svc__gamma": loguniform(1e-4, 1e1)},
                           n_iter=40, cv=5, random_state=0)
# nested CV: the whole search is the "model" scored by the outer loop
outer = cross_val_score(rand, X, y, cv=KFold(5, shuffle=True, random_state=1))
print("nested CV accuracy", outer.mean())

import optuna                                                       # TPE sampler + pruning
def objective(trial):
    lr    = trial.suggest_float("learning_rate", 1e-3, 0.3, log=True)
    depth = trial.suggest_int("max_depth", 2, 10)
    model = make_model(lr, depth)
    for step in range(100):
        model.train_one_epoch()
        score = model.validate()
        trial.report(score, step)
        if trial.should_prune(): raise optuna.TrialPruned()        # successive halving / Hyperband
    return score
study = optuna.create_study(direction="maximize", sampler=optuna.samplers.TPESampler(seed=0),
                            pruner=optuna.pruners.SuccessiveHalvingPruner())
study.optimize(objective, n_trials=100); print(study.best_params)
